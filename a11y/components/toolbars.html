Toolbars

A toolbar is a compact group of commonly used controls, such as buttons, toggle buttons, menu buttons, links, checkboxes, or other widgets. A toolbar reduces the number of tab stops by using arrow keys to move focus among its controls.

Toolbars differ from other grouped controls:

  • Use a toolbar when a compact set of related controls benefits from composite-widget keyboard navigation.
  • Use an ordinary group of buttons when arrow-key navigation and a reduced tab-stop count are unnecessary.
  • Use a menu button or menu for a compact list of commands that opens on demand rather than a permanently visible control group.
  • Use a tablist when controls select associated content panels.
  • Use a radiogroup when controls represent mutually exclusive choices.
  • Do not apply role="toolbar" merely because controls are aligned horizontally or visually styled as a toolbar.

WCAG requirements

  • The toolbar container exposes role="toolbar". (4.1.2)
  • The toolbar has a programmatically determinable accessible name that identifies its purpose. (1.3.1, 2.4.6, 4.1.2)
  • Each control in the toolbar has appropriate native or ARIA semantics, a programmatically determinable accessible name, and any required state or value. (4.1.2)
  • Buttons, toggle buttons, menu buttons, links, checkboxes, radio groups, spin buttons, and other controls within the toolbar follow the requirements for their respective control patterns. (2.1.1, 4.1.2)
  • The toolbar is operable using a keyboard. (2.1.1)
  • The sequential Tab order includes one normal tab stop for the toolbar. Arrow keys move focus among controls within the toolbar. (2.1.1, 2.4.3)
  • In a horizontal toolbar, Right Arrow and Left Arrow move focus between eligible controls. (2.1.1)
  • In a vertical toolbar, aria-orientation="vertical" is exposed and Down Arrow and Up Arrow move focus between eligible controls. (2.1.1, 4.1.2)
  • The toolbar's focus-management implementation maintains one appropriate control in the normal tab sequence and removes other managed controls from the sequential tab order. (2.4.3)
  • Keyboard focus moves through the toolbar in a logical order and does not enter disabled, hidden, or unavailable controls. (2.4.3, 4.1.2)
  • The focused toolbar control has a visible focus indicator. (2.4.7)
  • Focused controls are not completely hidden by sticky headers, banners, dialogs, or other author-created content. (2.4.11)
  • The toolbar does not create a keyboard trap. Users can move into and out of it with Tab and Shift+Tab. (2.1.2)
  • Control states, including pressed, selected, checked, expanded, disabled, and value states, are programmatically determinable and update when they change. (4.1.2)
  • Control states, groupings, and orientation are not conveyed by color alone. (1.4.1)
  • Toolbar labels, control labels, icons, boundaries needed to identify controls, state indicators, and focus indicators have sufficient contrast. (1.4.3, 1.4.11)
  • The toolbar remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • Toolbar controls meet the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • Moving focus within the toolbar does not cause an unexpected change of context. (3.2.1)
  • Activating a toolbar control does not cause an unexpected change of context unless the control's purpose and resulting behavior are understandable. (3.2.2)

Command buttons

A command button performs an action, such as Save, Print, Undo, Redo, Copy, Paste, or Delete.

  • Each command button has an accessible name that identifies its action. (2.4.6, 4.1.2)
  • Each command button is operable with the keyboard. (2.1.1)
  • If an action produces a status message without moving focus, the result is available to assistive technology. (4.1.3)
  • Destructive actions identify their consequences and provide appropriate safeguards when applicable. (3.3.4)

Toggle buttons

A toggle button changes between pressed and not-pressed states, such as Bold, Italic, Mute, or Show formatting marks.

  • The toggle button's pressed state is exposed with aria-pressed="true" or aria-pressed="false". (4.1.2)
  • The programmatic pressed state updates when the visual state changes. (4.1.2)
  • The pressed and not-pressed states are distinguishable without relying on color alone. (1.4.1)
  • The accessible name remains understandable across state changes. (4.1.2)

Menu buttons and overflow controls

A menu button or overflow control opens a menu of additional commands, such as a "More actions" button in a compact toolbar.

  • The control has an accessible name that identifies the menu or action category. (2.4.6, 4.1.2)
  • The control communicates that it opens a menu and exposes its expanded state when applicable. (4.1.2)
  • The menu button and its menu are keyboard-operable. (2.1.1)
  • Focus moves predictably into, through, and out of the menu. (2.1.2, 2.4.3)
  • Closing the menu returns focus to the menu button or another logical location. (2.4.3)

Radio groups and other composite controls

A toolbar may contain a radiogroup, slider, spin button, listbox, or another composite control. These controls require their own semantics and keyboard behavior.

  • The contained composite control exposes its appropriate role, name, states, and values. (4.1.2)
  • The toolbar's arrow-key navigation does not prevent users from operating the contained control with its required keys. (2.1.1)
  • Focus enters, operates within, and exits the contained control predictably. (2.1.1, 2.4.3)
  • The current value or selected state is programmatically determinable and updates when it changes. (4.1.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use a native <button>, <a>, form control, or other native control for each toolbar item whenever possible.
  • Give the toolbar a visible heading or label when its purpose is not obvious from nearby content.
  • Use an aria-label or aria-labelledby to name the toolbar, such as "Text formatting", "Document actions", or "Map controls".
  • Use roving tabindex to manage focus: one eligible control has tabindex="0", and other managed controls have tabindex="-1".
  • Return focus to the control that was most recently focused within the toolbar when users tab back into it, where practical.
  • Do not use positive tabindex values.
  • Keep the toolbar's arrow-key navigation separate from arrow keys needed to operate a contained control, such as a slider, spin button, radio group, listbox, or menu.
  • Group related commands and separate distinct command groups visually and semantically when useful.
  • Use separators, headings, or grouping when a long toolbar contains distinct clusters of controls.
  • Use stable control order. Do not reorder controls dynamically while users are navigating the toolbar unless necessary and clearly communicated.
  • Use concise visible labels or familiar icons. Icon-only controls need accessible names independent of their icons.
  • Do not rely on tooltips as the only accessible name for icon-only toolbar controls.
  • Keep disabled controls understandable. Do not make necessary controls unavailable without explaining how they become available.
  • When space is limited, provide an accessible overflow mechanism rather than clipping controls or making them unreachable.
  • Use a menu button or other accessible pattern for overflow controls such as "More actions".
  • Do not place controls in a toolbar when their primary interaction conflicts with the toolbar's arrow-key navigation and cannot be managed predictably.

Practical test sequence

Focus Details Applicable Criteria
Identify function
  • Confirm that toolbar is the correct pattern and that the component is a compact group of commonly used controls that benefits from a reduced number of tab stops. (1.3.1, 4.1.2)
  • Confirm that the component is not more accurately represented as an ordinary button group, menu, tablist, radiogroup, navigation region, or another pattern.
  • Determine whether the toolbar is horizontal or vertical.
  • Identify every contained control type, including command buttons, toggle buttons, menu buttons, links, inputs, sliders, radio groups, and overflow controls.
  • Determine whether controls use roving tabindex or another focus-management strategy.
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Semantics and language
  • Confirm that the container exposes role="toolbar". (4.1.2)
  • Confirm that the toolbar has a meaningful accessible name that identifies its purpose. (1.3.1, 2.4.6, 4.1.2)
  • For a vertical toolbar, confirm that it exposes aria-orientation="vertical". (4.1.2)
  • Confirm that every contained control exposes the correct role and has a meaningful accessible name. (4.1.2)
  • Confirm that visible control labels are included in accessible names. (2.5.3)
  • Confirm that icon-only controls have accessible names independent of their icons or tooltips. (1.1.1, 4.1.2)
  • Confirm that toggle, menu, disabled, expanded, selected, checked, and value states are exposed when applicable. (4.1.2)
  • Confirm that the toolbar's programmatic orientation, grouping, and control order match the visual presentation and intended interaction. (1.3.1, 4.1.2)

Screen reader
  • Confirm that the toolbar is announced with its accessible name and toolbar role. (4.1.2)
  • Confirm that each contained control is announced with its meaningful name, role, and relevant state or value. (4.1.2)
  • For toggle buttons, confirm that pressed or not-pressed state is announced and updates correctly. (4.1.2)
  • For menu buttons, confirm that the menu purpose, popup state, and expanded/collapsed state are available. (4.1.2)
  • For sliders, radio groups, inputs, or other complex controls, confirm that the current value or selection is announced correctly. (4.1.2)
  • For command actions that update the interface without moving focus, confirm that relevant success, failure, or completion messages are announced. (4.1.3)
  • Confirm that decorative icons, separators, and visual grouping elements are not announced unnecessarily. (1.1.1)

  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
Keyboard only
  • Use Tab and Shift+Tab to move into and out of the toolbar. Confirm that there is one normal tab stop for the managed toolbar controls. (2.1.1, 2.4.3)
  • Tab away from the toolbar and then tab back into it. Confirm that focus moves to the first eligible control on initial entry and, where implemented, returns to the most recently focused control on subsequent entry. (2.1.1, 2.4.3)
  • For a horizontal toolbar, use Right Arrow and Left Arrow to move focus to the next and previous eligible controls. Confirm the documented wrapping behavior at the first and last controls. (2.1.1)
  • For a vertical toolbar, use Down Arrow and Up Arrow to move focus to the next and previous eligible controls. Confirm the documented wrapping behavior at the first and last controls. (2.1.1)
  • Confirm that arrow-key navigation skips disabled, hidden, or unavailable controls as intended. (2.1.1, 4.1.2)
  • Operate every toolbar control with its expected keyboard commands, such as Enter, Space, arrow keys, or another documented interaction. (2.1.1)
  • For contained sliders, radio groups, spin buttons, listboxes, or menus, confirm that their required keys operate the contained control and do not incorrectly move toolbar focus. (2.1.1, 2.4.3)
  • Confirm that focus remains visible and is not completely hidden by other content. (2.4.7, 2.4.11)
  • Confirm that users can leave the toolbar with Tab and Shift+Tab and that it does not create a keyboard trap. (2.1.2)
  • Confirm that moving focus with arrow keys does not activate commands, open menus, change values, or otherwise cause an unexpected context change. (3.2.1)

Control behavior and results
  • Activate each command button and confirm that it produces the expected result. (2.1.1)
  • For toggle buttons, activate each control repeatedly and confirm that visible and programmatic states update together. (1.3.1, 4.1.2)
  • For menu buttons and overflow controls, confirm that menus open, close, and return focus predictably. (2.1.1, 2.1.2, 2.4.3)
  • For controls that affect other page content, confirm that the resulting change is understandable and announced as a status message when required. (1.3.1, 4.1.3)
  • For destructive, data-modifying, legal, or financial actions, confirm that appropriate review, confirmation, reversibility, or error prevention is provided when applicable. (3.3.4)
  • Confirm that disabled controls cannot be activated and that their unavailable state is communicated. (2.1.1, 4.1.2)
  • Confirm that activating a toolbar control does not move focus unexpectedly or cause an unexpected context change. (2.4.3, 3.2.2)

Inspect visual aspects
  • Check contrast for toolbar labels, control labels, icons, control boundaries when needed to identify controls, state indicators, separators, and focus indicators. (1.4.3, 1.4.11)
  • Confirm that focus, pressed, selected, checked, expanded, disabled, and unavailable states are not distinguished by color alone. (1.4.1)
  • Check the toolbar at 200% text resize, a 320-CSS-pixel-wide viewport, and with text-spacing overrides. Controls, labels, icons, overflow controls, instructions, and status messages must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm that responsive behavior does not clip, hide, or make toolbar controls unreachable. If controls move into an overflow mechanism, confirm that the mechanism remains operable and understandable. (1.4.10, 2.1.1)
  • Confirm that each toolbar control meets the minimum target size or has sufficient spacing from adjacent targets. (2.5.8)
  • Confirm that the focus indicator is visible against surrounding colors and is not completely hidden by other content. (1.4.11, 2.4.11)
  • Confirm disabled styling does not make a control's label, icon, state, or availability impossible to understand when users need that information. (1.4.3, 1.4.11)
