Tables and grids

Tables and grids organize related information into rows and columns. They may present static data, support actions on individual rows, allow sorting or filtering, or provide a spreadsheet-like interface for viewing and editing information.

Tables and grids differ from related components:

  • Use a native HTML table for static tabular data and for data that users need to compare across rows and columns.
  • Use a native HTML table when table cells contain ordinary links, buttons, form controls, or disclosure controls that can follow the normal keyboard tab order.
  • Use an ARIA table only when native HTML table markup cannot be used for a static tabular structure.
  • Use a grid only when users need two-dimensional keyboard navigation, spreadsheet-like editing, row selection, cell selection, or another behavior that requires managed focus within rows and cells.
  • Do not use a table for layout. Use CSS layout techniques for visual positioning of unrelated content.
  • Do not use a grid merely to make a data table appear modern, scrollable, sortable, or responsive.
  • Do not make every data cell focusable unless cell-by-cell keyboard navigation is needed for the user task.

WCAG requirements

  • Data-table structure, including headers, cells, captions, and row or column relationships, is programmatically determinable. (1.3.1)
  • Header cells are correctly associated with the data cells they describe. (1.3.1)
  • The reading order of table content, controls, and responsive alternatives preserves a meaningful sequence. (1.3.2)
  • Information such as sort direction, selected rows, expanded details, required fields, errors, and disabled states is not conveyed by visual styling or color alone. (1.4.1, 4.1.2)
  • Table and grid text, including captions, headers, cell content, instructions, sort indicators, and control labels, has sufficient contrast. (1.4.3)
  • Meaningful non-text indicators, including focus indicators, sort icons, selected-row boundaries, checkbox states, grid lines when needed for interpretation, and controls, have sufficient non-text contrast. (1.4.11)
  • All table and grid controls are keyboard-operable. (2.1.1)
  • Keyboard focus can move into and out of an interactive grid without a keyboard trap. (2.1.2)
  • Keyboard focus order is logical and preserves the intended relationship among cells, controls, rows, and columns. (2.4.3)
  • Keyboard focus is visible on interactive controls, focusable cells, selected cells, rows, and other focusable grid elements. (2.4.7)
  • Keyboard focus is not completely hidden by sticky headers, sticky columns, overlays, menus, dialogs, or other author-created content. (2.4.11)
  • Interactive rows, cells, headers, controls, and grid elements have programmatically determinable names, roles, states, values, and relevant relationships. (4.1.2)
  • Changes resulting from sorting, filtering, pagination, loading additional rows, row selection, cell editing, or validation errors are communicated to assistive technology when users need the information. (4.1.3)
  • Touch targets for interactive table and grid controls meet the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • Drag-and-drop reordering, column resizing, or row movement has a non-dragging alternative when applicable. (2.5.7)
  • Table or grid controls do not unexpectedly change context when they receive focus or when users provide input. (3.2.1, 3.2.2)

Native data tables

A native data table uses semantic HTML table elements to communicate the relationships between data cells and their row and column headers. A static data table is not a composite keyboard widget: its cells are not normally focusable or selectable.

  • The table uses native <table> markup for tabular data. (1.3.1)
  • The table has a caption, visible heading, or accessible name that identifies its topic or purpose. (1.3.1, 2.4.6)
  • Column headers and row headers use <th> elements rather than visually styled data cells. (1.3.1)
  • Header cells use appropriate scope values or explicit headers associations when needed to define their relationship to data cells. (1.3.1)
  • Data cells use <td> elements. (1.3.1)
  • Complex header relationships, including grouped, irregular, multi-level, or spanning headers, are programmatically determinable. (1.3.1)
  • Table sections are marked up appropriately when they help communicate structure, such as with <thead>, <tbody>, and <tfoot>. (1.3.1)
  • Controls within table cells, such as links, buttons, checkboxes, inputs, menus, or disclosure controls, are keyboard-operable and have accessible names. (2.1.1, 4.1.2)
  • Keyboard focus follows a logical reading and interaction order through controls contained in the table. (2.4.3)

Sortable, filterable, and paginated tables

A sortable, filterable, or paginated table remains a table when users interact with ordinary controls and do not need cell-by-cell keyboard navigation. Sorting, filtering, search, pagination, and row actions do not by themselves require a grid pattern.

  • Sort controls are keyboard-operable and have meaningful accessible names. (2.1.1, 4.1.2)
  • The current sort column and sort direction are programmatically determinable, such as through aria-sort on the relevant column header where appropriate. (1.3.1, 4.1.2)
  • Sorting is not indicated by color, icon direction, or visual position alone. (1.4.1)
  • When sorting, filtering, searching, or changing pages updates the displayed data, users receive an appropriate status message when needed. (4.1.3)
  • Filters have visible labels, accessible names, and clear instructions when the available data or table behavior is not obvious. (3.3.2, 4.1.2)
  • Filtering, sorting, or entering a search query does not unexpectedly move focus, submit content, navigate users away, or change context unless the behavior is clearly expected. (3.2.1, 3.2.2)
  • Pagination controls identify the current page and are keyboard-operable. (2.1.1, 4.1.2)
  • When pagination or filtering changes the table, focus is managed so that users can locate the updated results without losing context. (2.4.3, 4.1.3)
  • Selected rows, selected records, bulk-action availability, and row counts are programmatically determinable when applicable. (1.3.1, 4.1.2, 4.1.3)

Interactive grids

An interactive grid is a composite widget that presents information in rows and columns and uses a managed keyboard model. It is appropriate for spreadsheet-like interfaces, cell selection, row selection, editable cells, or dense applications where users need efficient directional navigation among cells.

  • The grid is used only when its cell-based interaction model provides a meaningful benefit over a semantic table with standard controls. (1.3.1)
  • The grid has an accessible name and, when needed, an accessible description explaining its purpose and keyboard interaction model. (4.1.2, 3.3.2)
  • The grid exposes appropriate semantics, such as role="grid", role="row", role="gridcell", role="columnheader", and role="rowheader", when native HTML semantics cannot provide the required interaction. (1.3.1, 4.1.2)
  • The grid manages focus so that keyboard users can enter the grid, navigate its intended cells and controls, and leave it. (2.1.1, 2.1.2)
  • Only the intended grid cell or active descendant receives focus at a time, unless another documented keyboard model is required. (2.4.3, 4.1.2)
  • Arrow-key navigation follows the intended row and column relationships. (2.1.1, 2.4.3)
  • Grid keyboard commands do not conflict with standard assistive-technology or browser behavior without providing an accessible and documented interaction method. (2.1.1)
  • Focused cells, selected cells, editable cells, disabled cells, row and column headers, and other states are programmatically determinable. (1.3.1, 4.1.2)
  • Focus remains visible and is not obscured when the grid scrolls, uses sticky rows or columns, or opens overlays. (2.4.7, 2.4.11)
  • Users can identify the active row, column, cell, selection, edit mode, sort state, and validation state when applicable. (1.3.1, 4.1.2)
  • If the grid virtualizes rows or columns, assistive technologies receive accurate row, column, and position information. (1.3.1, 4.1.2)
  • Grid updates, loading states, changed selections, successful edits, and validation errors are communicated when users need the information. (4.1.3)

Grid keyboard interaction

The following is a common grid pattern. Implement only the commands appropriate to the grid's features and clearly document any nonstandard commands.

  • Tab moves focus into the grid, and Shift+Tab moves focus away from the grid. (2.1.1, 2.1.2)
  • Arrow keys move focus among cells according to the grid's row and column structure. (2.1.1)
  • Home moves to the first cell in the current row, and End moves to the last cell in the current row when those commands are supported. (2.1.1)
  • Ctrl+Home moves to the first cell in the grid, and Ctrl+End moves to the last cell in the grid when those commands are supported. (2.1.1)
  • Page Up and Page Down move focus by a predictable group of rows when the grid displays a large or virtualized data set and these commands are supported. (2.1.1)
  • Enter, Space, or another documented key activates a control, enters cell edit mode, selects a row, or performs another stated action. (2.1.1, 4.1.2)
  • Escape exits cell edit mode, dismisses a grid popup, cancels an in-progress action, or returns focus to the intended grid context when applicable. (2.1.2)
  • When a cell contains multiple interactive controls, the grid provides a predictable method for entering and leaving the cell's internal controls. (2.1.1, 2.4.3)

Editable tables and grids

An editable table or grid lets users change values directly within rows or cells. Editable cells require clear interaction instructions and reliable feedback for validation, saving, cancellation, and errors.

  • Users can identify which cells or rows are editable, required, read-only, disabled, selected, or invalid without relying on color alone. (1.4.1, 4.1.2)
  • Users can enter, edit, save, and cancel cell changes using a keyboard. (2.1.1)
  • Each editable field has an accessible name that identifies the relevant row, column, and expected input. (1.3.1, 3.3.2, 4.1.2)
  • Instructions explain how to enter edit mode, navigate between editable cells, save changes, and cancel changes when the behavior is not standard or obvious. (3.3.2)
  • Validation errors identify the affected cell or field and describe the problem in text. (3.3.1, 3.3.3)
  • Errors and successful save states are communicated to assistive technologies when users need the information. (4.1.3)
  • Editing a cell does not unexpectedly submit the entire form, move users to a different context, or discard work. (3.2.2)
  • If a confirmation step is needed before destructive actions, users can review, correct, or reverse the action as appropriate. (3.3.4)

Responsive tables

Responsive table behavior must preserve the data relationships users need to understand. A table may scroll horizontally, reflow into labeled records, expose selected columns, or provide an alternate view, provided that the essential information and relationships remain available.

  • At narrow widths and with enlarged text, essential table data, headers, labels, controls, and relationships remain available. (1.3.1, 1.4.10)
  • If a table becomes horizontally scrollable, users can reach and operate all controls and read all columns without content being clipped or obscured. (2.1.1, 1.4.10)
  • If rows reflow into cards or another small-screen layout, each value retains a visible or programmatically determinable label that identifies its original column header. (1.3.1)
  • Sticky headers and sticky columns do not cover focused controls, selected cells, error messages, or needed data. (2.4.11)
  • Text remains readable and does not overlap, clip, or become unusable when text is resized or text spacing is increased. (1.4.4, 1.4.10, 1.4.12)

Best practices

These practices improve usability and maintainable implementation, although not all are independent WCAG requirements in every situation.

  • Use native semantic HTML, including <table>, <caption>, <th>, <td>, and scope, before considering ARIA.
  • Give each data table a concise, descriptive caption that identifies the data's subject, scope, or purpose.
  • Use visible column and row headers whenever users need them to understand a cell's value.
  • Use scope="col" for column headers and scope="row" for row headers when applicable.
  • For complex tables with multi-level, irregular, grouped, or spanning headers, use scope="colgroup", scope="rowgroup", or explicit id and headers associations as appropriate.
  • Keep tables as simple as possible. Split very complex tables into smaller related tables, summaries, or alternative views when doing so improves comprehension.
  • Provide a summary or instructions before a complex table when users need help understanding its purpose, hierarchy, abbreviations, controls, calculations, or navigation.
  • Use visible labels and clear instructions for table filters, sorting controls, pagination, row actions, bulk actions, and editable cells.
  • For sortable columns, expose the current sort column and direction programmatically, and use text or another non-color indicator in addition to a visual icon.
  • For responsive designs, preserve the relationship between headers and data cells. Do not hide headers or create ambiguous card layouts without supplying the necessary labels.
  • Consider a horizontally scrollable wrapper for wide data tables rather than restructuring the table in a way that loses row and column context.
  • Keep column headers visible while scrolling long tables when doing so helps users compare data, but do not obscure keyboard focus or table content.
  • Use a standard table with normally tabbable controls in cells when that interaction model is sufficient.
  • Use a managed-focus grid only when its added keyboard model is necessary and documented for users.
  • When a grid includes editable cells, provide clear instructions for entering edit mode, saving changes, cancelling changes, and returning to grid navigation.
  • Do not use role="grid", role="table", or other ARIA table roles to repair an incorrectly marked-up native table when native HTML semantics can be used instead.
  • Test with realistic data volumes, long values, narrow viewports, enlarged text, keyboard-only navigation, and a screen reader.

Practical test sequence

Identify structure
  • Determine whether the component is a static data table, a table with ordinary controls, an ARIA table, or a managed-focus interactive grid. (1.3.1, 4.1.2)
  • Determine whether users need only to read data, activate controls within rows, sort or filter results, select rows, edit cells, or navigate cell by cell.
  • Identify all structural information: caption, heading, column headers, row headers, grouped headers, table sections, totals, summaries, filters, sort controls, pagination, row actions, and bulk actions. (1.3.1)
  • Identify every interactive function, including sorting, filtering, searching, pagination, expanding rows, selecting rows, editing cells, resizing columns, reordering rows or columns, exporting, and bulk actions.

Table semantics
  • Confirm that tabular data exposes programmatically determinable table, row, cell, and header relationships. Native HTML table markup or appropriate ARIA table or grid semantics may be used. (1.3.1)
  • If native HTML table markup is used, confirm that the structure uses appropriate <table>, <tr>, <th>, and <td> elements. (1.3.1)
  • If role="table" or role="grid" is used, confirm that rows use role="row" and that cells and headers are contained within the appropriate rows. (1.3.1, 4.1.2)
  • Confirm that the table or grid has a descriptive visible heading, caption, or accessible name that identifies its topic or purpose. (1.3.1, 2.4.6)
  • For native HTML tables, confirm that column and row headers use <th> elements. For ARIA tables and grids, confirm that column headers use role="columnheader" and row headers use role="rowheader", as applicable. (1.3.1)
  • For native HTML tables, confirm that column headers, row headers, and grouped headers are associated with the correct data cells using scope, id, and headers as needed. (1.3.1)
  • For ARIA tables, confirm that data cells use role="cell". For grids, confirm that data cells use role="gridcell". (1.3.1, 4.1.2)
  • For complex tables and grids, confirm that multi-level, irregular, spanning, row-group, and column-group header relationships are programmatically determinable. (1.3.1)
  • Confirm that visual styling, responsive behavior, and sticky positioning do not alter or obscure the intended reading sequence. (1.3.2)

Screen reader

  • For complex tables, test cells in each header configuration and confirm that every relevant header relationship is available. (1.3.1)
  • Confirm that totals, units, abbreviations, calculations, footnotes, and exceptions are understandable in context. (1.3.1)
  • For sortable columns, confirm that the sort control, current sort state, and sort direction are announced. (4.1.2)
  • For selected rows, expandable rows, editable cells, or validation states, confirm that the relevant state is announced. (4.1.2)
  • Apply filters, change sorting, paginate, select rows, edit cells, and load additional data. Confirm that relevant changes and status messages are announced. (4.1.3)
  • For a grid, confirm that its name, instructions, active cell, row and column context, selection, edit mode, and other required states are available. (1.3.1, 4.1.2)

Keyboard only
  • Use Tab and Shift+Tab to reach and move away from table controls, including filters, sort buttons, row actions, checkboxes, pagination, editable fields, bulk actions, and download controls. (2.1.1, 2.4.3)
  • Confirm that ordinary table cells are not unnecessarily added to the tab order. (2.4.3)
  • For an interactive grid, use the documented key commands to enter the grid, navigate among cells, activate controls, enter and leave edit mode, select rows or cells, and leave the grid. (2.1.1, 2.1.2)
  • Confirm that users can escape grid edit modes, menus, popups, or cell-contained controls without becoming trapped. (2.1.2)
  • Confirm that keyboard focus is visible on every interactive control, focused grid cell, selected item, editable field, and active row or column header. (2.4.7)
  • Confirm that sticky headers, sticky columns, floating controls, tooltips, menus, and overlays do not completely hide focus. (2.4.11)
  • Confirm that focus order follows the intended interaction sequence and does not jump unexpectedly after sorting, filtering, pagination, inline editing, or row expansion. (2.4.3, 3.2.1, 3.2.2)
  • Confirm that drag-based row or column reordering and resizing have keyboard-accessible or non-dragging alternatives when those functions are available. (2.1.1, 2.5.7)

Visual and responsive behavior
  • Confirm that headers, sort direction, selected rows, expanded rows, required fields, errors, disabled cells, and other meaningful states are not indicated by color alone. (1.4.1)
  • Check contrast for table text, captions, headers, labels, cell content, status messages, and control labels. (1.4.3)
  • Check non-text contrast for control boundaries, checkboxes, sort icons, focus indicators, selection indicators, error icons, grid lines when necessary for comprehension, and other meaningful graphical objects. (1.4.11)
  • Resize text to 200% and confirm that table content, controls, labels, and actions remain readable and usable. (1.4.4)

  • Apply text-spacing overrides and confirm that text does not overlap, clip, or become unusable. (1.4.12)
