Radio buttons

Radio buttons are form controls that allow a user to select one option from a group of mutually exclusive options. Selecting one radio button deselects any other selected radio button in the same group.

Radio buttons differ from other controls:

  • Use radio buttons when users must select one option from a small, visible group of mutually exclusive choices.
  • Use a checkbox when users can select zero, one, or multiple independent options.
  • Use a native <select> when users must select one option from a larger list, especially when screen space is limited.
  • Use a switch when a control immediately turns a single setting or service on or off.
  • Use a native <input type="radio"> whenever possible.

WCAG requirements

  • Each radio button has a programmatically determinable accessible name. (4.1.2)
  • Each radio button exposes radio-button semantics. A native <input type="radio"> provides this role automatically. (4.1.2)
  • Custom radio buttons use role="radio" and keep aria-checked synchronized with the visual state. (4.1.2)
  • The selected and unselected states are programmatically determinable and update when the selection changes. (4.1.2)
  • Only one radio button in a radio group is selected at a time, unless no selection is allowed before the user makes a choice. (1.3.1, 4.1.2)
  • Each radio group has a programmatically determinable accessible name that identifies the question, category, or purpose of the group. (1.3.1, 2.4.6)
  • A native group uses radio inputs with the same name value and is grouped with a <fieldset> and <legend> when the group has a common question or purpose. (1.3.1)
  • A custom radio group uses role="radiogroup" and has an accessible name, such as through aria-labelledby. (1.3.1, 4.1.2)
  • Each radio button has a visible label that is associated with it programmatically. (1.3.1, 3.3.2)
  • The visible label is included in the radio button's accessible name. (2.5.3)
  • The radio group is operable with a keyboard. (2.1.1)
  • The radio buttons can be reached and operated in a logical focus order. (2.4.3)
  • The focused radio button has a visible focus indicator. (2.4.7)
  • The selected state is not conveyed by color alone. (1.4.1)
  • The radio button, label, selected-state indicator, and focus indicator have sufficient contrast. (1.4.3, 1.4.11)
  • The radio group remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • The pointer target meets the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • A radio button that is disabled or unavailable exposes that state programmatically and does not respond as an available radio button. (4.1.2)
  • If a radio group is required, the required status and any resulting validation errors are communicated to users. (1.3.1, 3.3.1, 3.3.2, 4.1.2)
  • Changing a radio-button selection does not automatically submit a form or cause an unexpected change of context unless the behavior is clearly communicated and appropriate. (3.2.2)
  • When choosing a radio option reveals dependent content, keep the relationship clear and do not unexpectedly move focus into the revealed content. (1.3.1, 3.2.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use native <input type="radio"> elements with associated <label> elements whenever possible.
  • Use a <fieldset> and <legend> for every related group of native radio buttons.
  • Use concise labels that describe the available choices, such as Email, Phone, and Text message.
  • Use a group label that asks the question or identifies the category, such as Preferred contact method.
  • Make the visible label clickable in addition to the radio button itself.
  • Make the entire radio button and label area an adequate activation target. Using a properly associated <label> does this automatically.
  • Present radio options in a meaningful order, such as chronological, alphabetical, most-to-least common, or a logical task sequence.
  • Do not use radio buttons when users need to select more than one option.
  • Do not use radio buttons when users can reasonably make no selection and a checkbox or another control would better express the choice.
  • Do not use aria-checked on native radio buttons. The native selected state is exposed automatically.
  • Do not make a default selection unless a choice is genuinely more likely, safer, or otherwise appropriate for most users.
  • Do not use a selected radio button as a substitute for a submit or confirmation action.
  • Place shared instructions, required information, descriptions, and error messages near the group and associate them with the group where possible.
  • Ensure selected, unselected, disabled, hover, and focus states are visually distinguishable.

Practical test sequence

Focus Details Applicable Criteria
Identify function
  • Confirm that radio is the correct role and that users are expected to select only one option from the group. (1.3.1, 4.1.2)
  • Confirm that a radio group is the appropriate pattern rather than a checkbox group, select, combobox, switch, tab list, or another control.
  • Determine whether the component uses native HTML radio buttons or a custom ARIA radio group.
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Semantics and language
  • Confirm each radio button is a native <input type="radio"> where feasible, or exposes role="radio". (4.1.2)
  • Confirm that native radio buttons in the same group share the same name value. (1.3.1)
  • Confirm each radio button has a visible, descriptive label associated with it using a <label>, for/id, or an equivalent valid method. (1.3.1, 4.1.2)
  • Confirm the accessible name contains the visible label text. (2.5.3)
  • Confirm the group has a meaningful visible label, such as a <legend> associated with a <fieldset>. (1.3.1, 2.4.6)
  • For a custom radio group, confirm that the container uses role="radiogroup" and has an accessible name. (1.3.1, 4.1.2)
  • Confirm that the radio group represents mutually exclusive choices rather than independent selections. (1.3.1, 4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 2.4.6 Headings and Labels (Level AA)
  • WCAG 2.2: Understanding SC 2.5.3 Label in Name (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Confirm each control is announced as a radio button. (4.1.2)
  • Verify that each radio button has a meaningful accessible name. (4.1.2)
  • Confirm that the group label, relevant instructions, required status, and error messages are available to assistive technology. (1.3.1, 3.3.1, 3.3.2, 4.1.2)
  • Verify that each radio button's selected or unselected state is announced on focus. (4.1.2)
  • Verify that users can determine which radio button is selected and that only one option is selected at a time. (4.1.2)
  • Select a different option and confirm that the announced state updates correctly for the newly selected and previously selected options. (4.1.2)
  • If a radio button is disabled, confirm that its unavailable state is announced. (4.1.2)
  • When selecting an option reveals, hides, or changes additional content, confirm that the resulting content and relationship are understandable. (1.3.1, 4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.2 Labels or Instructions (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Keyboard only
  • Use Tab and Shift+Tab to move into and out of the radio group. When a native group has a selected radio button, focus should move to the selected radio button. If no radio button is selected, focus should move to the first radio button in the group. (2.1.1, 2.4.3)
  • Use Down Arrow and Right Arrow to move to and select the next radio button. Use Up Arrow and Left Arrow to move to and select the previous radio button. Confirm that arrow-key navigation wraps from the last option to the first and from the first option to the last, where the standard radio-group pattern is implemented. (2.1.1)
  • Use Space to select a focused radio button when it is not already selected. (2.1.1)
  • Confirm that pressing Enter does not cause unexpected behavior. Native radio buttons are normally selected with Space; custom implementations should follow the appropriate radio-group pattern. (2.1.1)
  • Confirm that the focused radio button has a visible focus indicator and is not completely hidden by other content. (2.4.7, 2.4.11)
  • Confirm that the radio group does not create a keyboard trap and that focus moves in a logical order before and after the group. (2.1.2, 2.4.3)
  • Confirm that a disabled radio button cannot be selected or activated. (2.1.1)
  • Confirm that changing the selection does not unexpectedly submit a form, open a dialog, move focus, or cause another unexpected change of context. (2.4.3, 3.2.1, 3.2.2)
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 2.1.2 No Keyboard Trap (Level A)
  • WCAG 2.2: Understanding SC 2.4.3 Focus Order (Level A)
  • WCAG 2.2: Understanding SC 2.4.7 Focus Visible (Level AA)
  • WCAG 2.2: Understanding SC 2.4.11 Focus Not Obscured (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 3.2.1 On Focus (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
Forms and validation
  • For required radio groups, submit the form without selecting an option and confirm that it is identified as needing attention. (3.3.1)
  • Confirm that the error message identifies the radio group and explains what must be done. (3.3.1, 3.3.3)
  • Confirm that the error message is programmatically associated with the radio group. (1.3.1)
  • Confirm that users can identify and correct the error without relying only on color, position, or visual styling. (1.4.1, 3.3.1)
  • Confirm that the selected radio-button value is submitted as intended. (4.1.2)
  • Confirm that selecting a radio button does not automatically submit the form or change context unexpectedly. (3.2.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 1.4.1 Use of Color (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.3 Error Suggestion (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Conditional content
  • When a radio-button selection reveals, hides, enables, disables, or changes other content, confirm that the relationship is understandable visually and programmatically. (1.3.1, 4.1.2)
  • Confirm that newly available content appears in a logical reading and focus order. (1.3.2, 2.4.3)
  • Confirm that hidden or disabled content cannot receive keyboard focus or be operated as though it were available. (2.1.1, 2.4.3, 4.1.2)
  • Confirm that selecting a radio button does not unexpectedly move focus into the newly revealed content. (2.4.3, 3.2.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 1.3.2 Meaningful Sequence (Level A)
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 2.4.3 Focus Order (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Inspect visual aspects
  • Check contrast for the radio buttons, labels, focus indicator, and selected-state indicator. (1.4.3, 1.4.11)
  • Confirm that selected and unselected states are not distinguished by color alone. (1.4.1)
  • Check the radio group at 200% text resize, a 320-CSS-pixel-wide viewport, and with text-spacing overrides. Radio buttons, labels, instructions, and error messages must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm that each radio button and its associated label provide an adequate pointer target. (2.5.8)
  • Confirm that the focus indicator is visible against the surrounding colors and is not completely hidden by other content. (1.4.11, 2.4.11)
  • Confirm disabled styling does not make labels, group instructions, or the selected state impossible to understand when users need that information. (1.4.3, 1.4.11)

  • WCAG 2.2: Understanding SC 1.4.4 Resize Text (Level AA)
  • WCAG 2.2: Understanding SC 1.4.10 Reflow (Level AA)
  • WCAG 2.2: Understanding SC 1.4.11 Non-text Contrast (Level AA)
