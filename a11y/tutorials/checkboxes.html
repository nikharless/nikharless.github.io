Checkboxes

A checkbox is a form control that allows a user to select or deselect an option. Checkboxes are appropriate when users can select one or more independent options from a group.

A checkbox differs from other controls:

  • Use a checkbox when an option can be selected independently of other options.
  • Use a radio button when a user must select exactly one option from a group.
  • Use a switch when the control immediately turns a setting or service on or off.
  • Use a disclosure button when the control shows or hides content rather than selecting an option.
  • Use a native <input type="checkbox"> whenever possible.

WCAG requirements

  • Each checkbox has a programmatically determinable accessible name. (4.1.2)
  • The checkbox exposes the checkbox role. A native <input type="checkbox"> provides this role automatically. (4.1.2)
  • For a custom checkbox, use role="checkbox" and keep aria-checked synchronized with the visual state. (4.1.2)
  • The checked or unchecked state is programmatically determinable and updates when the state changes. (4.1.2)
  • Use aria-checked="mixed" only when a tri-state checkbox genuinely represents a partially selected state. Do not use the indeterminate state merely as a decorative visual style. It should represent a meaningful relationship, such as a parent option with only some child options selected. (1.3.1, 4.1.2)
  • A visible label identifies the checkbox and is associated with it programmatically. (1.3.1, 3.3.2)
  • The visible label is included in the checkbox's accessible name. (2.5.3)
  • The checkbox is operable with a keyboard. (2.1.1)
  • The checkbox has a visible focus indicator when it receives keyboard focus. (2.4.7)
  • The checkbox can be reached and operated in a logical focus order. (2.4.3)
  • The checked state is not conveyed by color alone. (1.4.1)
  • The checkbox, label, and state indicator have sufficient contrast. (1.4.3, 1.4.11)
  • The checkbox remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • The pointer target meets the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • A checkbox that is disabled or unavailable exposes that state programmatically and does not respond as an available checkbox. (4.1.2)
  • If a group of checkboxes has a common purpose, the group has an appropriate programmatic label. (1.3.1, 2.4.6)
  • If a checkbox controls another part of the interface, the relationship and resulting state are programmatically determinable. (1.3.1, 4.1.2)
  • If a checkbox is required, the required status and any resulting validation errors are communicated to users. (1.3.1, 3.3.1, 4.1.2)
  • Do not automatically submit a form or cause an unexpected context change when a checkbox is selected unless the behavior is clearly communicated and appropriate. (3.2.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use a native <input type="checkbox"> with a <label> whenever possible.
  • Make the visible label clickable in addition to the checkbox itself.
  • Make the entire checkbox and label area an adequate activation target.
  • Use concise labels that describe the option, such as Send me email updates.
  • Do not change the label from one state to another, such as changing Enable notifications to Disable notifications. The checked state communicates the current state.
  • Use a <fieldset> and <legend> for a related group of checkboxes when the group has a common question or purpose.
  • Do not use a checkbox when selecting it immediately turns a setting on or off and a switch would better communicate that behavior.
  • Do not use aria-checked on a native checkbox. The native checked state is exposed automatically.
  • Place additional instructions, error messages, and descriptions so they are visually associated with the checkbox or group.
  • Do not disable a checkbox merely to prevent validation errors when users could instead receive an explanation and correct the problem.
  • Ensure checked, unchecked, indeterminate, disabled, hover, and focus states are visually distinguishable.

Practical test sequence

Focus Details Applicable Criteria
Semantics and language
  • Confirm each checkbox is a native <input type="checkbox"> where feasible, or exposes the checkbox role. (4.1.2)
  • Confirm each checkbox has a visible, descriptive label associated with it using a <label>, for/id, or an equivalent valid method. (1.3.1, 4.1.2)
  • Confirm the accessible name contains the visible label text. (2.5.3)
  • For a related group, confirm the group has an appropriate label, such as a <legend> associated with a <fieldset>. (1.3.1, 2.4.6)
  • Confirm the checkbox is used for an independent selectable option rather than a mutually exclusive choice, disclosure, or immediate on/off setting. (1.3.1, 4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 2.4.6 Headings and Labels (Level AA)
  • WCAG 2.2: Understanding SC 2.5.3 Label in Name (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Confirm the control is announced as a checkbox. (4.1.2)
  • Verify that each checkbox has a meaningful accessible name. (4.1.2)
  • Verify that the checked or unchecked state is announced on focus. (4.1.2)
  • Select and deselect each checkbox and confirm the announced state changes correctly. (4.1.2)
  • If a checkbox is disabled, confirm that its unavailable state is announced. (4.1.2)
  • If a checkbox is indeterminate, confirm that the mixed state is communicated when the state is meaningful. (4.1.2)
  • For a group of checkboxes, confirm that the group label and relevant instructions are available to assistive technology. (1.3.1)
  • Confirm that descriptions, required information, and error messages are associated with the checkbox or group. (1.3.1, 3.3.1, 4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Keyboard only
  • Use Tab and Shift+Tab to move to and away from each checkbox. (2.1.1, 2.1.2, 2.4.3)
  • Confirm that Space checks and unchecks the checkbox. (2.1.1)
  • Confirm that pressing Enter does not cause unexpected behavior. Native checkboxes are normally activated with Space; custom implementations should follow the appropriate checkbox pattern. (2.1.1)
  • Confirm that the checkbox has a visible focus indicator. (2.4.7)
  • Confirm that the checkbox and its associated label appear in a logical focus order. (2.4.3)
  • Confirm that a disabled checkbox cannot be operated. (2.1.1, 4.1.2)
  • Confirm that selecting the checkbox does not create an unexpected keyboard trap or context change. (2.1.2, 3.2.2)
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 2.1.2 No Keyboard Trap (Level A)
  • WCAG 2.2: Understanding SC 2.4.3 Focus Order (Level A)
  • WCAG 2.2: Understanding SC 2.4.7 Focus Visible (Level AA)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Forms and validation
  • Submit the form with the checkbox unselected and confirm that a required checkbox is identified as needing attention. (3.3.1)
  • Confirm the error message identifies the checkbox or group and explains what must be done. (3.3.1, 3.3.3)
  • Confirm the error message is programmatically associated with the checkbox or group. (1.3.1)
  • Confirm the user can identify and correct the error without relying only on color, position, or visual styling. (1.4.1, 3.3.1)
  • Confirm that checked values are submitted when appropriate and unchecked values are handled as intended. (4.1.2)
  • Confirm that selecting or clearing the checkbox does not submit the form or change context unexpectedly. (3.2.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 1.4.1 Use of Color (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.3 Error Suggestion (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Inspect visual aspects
  • Check contrast for the checkbox, label, focus indicator, and checked-state indicator. (1.4.3, 1.4.11)
  • Confirm checked and unchecked states are not distinguished by color alone. (1.4.1)
  • Check the checkbox at 200% text resize, a 320-CSS-pixel-wide viewport, and with text-spacing overrides. The checkbox, label, instructions, and error messages must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm the checkbox and its associated label provide an adequate pointer target. (2.5.8)
  • Confirm the focus indicator is visible against the surrounding colors and is not completely hidden by other content. (1.4.11, 2.4.11)
  • Confirm disabled styling does not make the label or state impossible to understand when users need that information. (1.4.3, 1.4.11)

  • WCAG 2.2: Understanding SC 1.4.3 Contrast (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 1.4.4 Resize Text (Level AA)
  • WCAG 2.2: Understanding SC 1.4.10 Reflow (Level AA)
  • WCAG 2.2: Understanding SC 1.4.11 Non-text Contrast (Level AA)
  • WCAG 2.2: Understanding SC 1.4.12 Text Spacing (Level AA)
  • WCAG 2.2: Understanding SC 2.4.11 Focus Not Obscured (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 2.5.8 Target Size (Minimum) (Level AA)
Tri-state and dependent checkboxes
  • If a parent checkbox represents child selections, confirm that checked, unchecked, and partially checked states accurately reflect the child checkboxes. (4.1.2)
  • Confirm that the mixed state is communicated to assistive technologies when it is exposed visually. (1.3.1, 4.1.2)
  • Select and clear child checkboxes and confirm that the parent state updates correctly. (4.1.2)
  • Confirm that selecting or clearing a parent checkbox produces the intended result for its child checkboxes. (4.1.2)
  • Confirm that the relationship between the parent and child options is understandable visually and programmatically. (1.3.1)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
