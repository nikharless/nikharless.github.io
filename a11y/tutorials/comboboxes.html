Comboboxes

A combobox is an input or select-like control that allows a user to choose a value from a popup list of options. A combobox may be select-only, or it may allow users to enter text and receive autocomplete suggestions.

Comboboxes differ from related controls:

  • Use a native <select> when users choose one option from a fixed list and text entry or custom behavior is not needed.
  • Use an editable combobox when users can enter text and may optionally choose a matching suggestion.
  • Use a listbox when the options are persistently displayed rather than shown in a popup.
  • Use a menu button for a list of commands or navigation links rather than a list of values.
  • Use a multiselect listbox or a group of checkboxes when users can select multiple values. Do not represent a multi-select control as a single-select combobox.
  • Prefer native HTML controls when they provide the required behavior.

WCAG requirements

  • The combobox has a visible label and a programmatically determinable accessible name. (1.3.1, 3.3.2, 4.1.2)
  • The control exposes the combobox role, or uses a native control with equivalent semantics. (4.1.2)
  • The expanded or collapsed state of the popup is programmatically determinable. (4.1.2)
  • The relationship between the combobox and its popup list is programmatically determinable. (1.3.1, 4.1.2)
  • The popup has the appropriate role, such as listbox, and its options have appropriate option semantics. (1.3.1, 4.1.2)
  • The combobox and its popup can be operated using a keyboard. (2.1.1)
  • Keyboard focus remains visible and is not completely hidden by other content. (2.4.7, 2.4.11)
  • Users can move through the options, identify the current option, and accept or dismiss a selection. (2.1.1, 4.1.2)
  • The current value, selected option, and active option are exposed and updated when they change. (4.1.2)
  • The combobox has a logical focus order and does not create a keyboard trap. (2.1.2, 2.4.3)
  • The visible label is included in the accessible name. (2.5.3)
  • Instructions, required status, descriptions, and error messages are programmatically associated with the combobox where applicable. (1.3.1, 3.3.1, 3.3.2, 4.1.2)
  • The combobox and popup options remain usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • Text, borders, option states, and focus indicators have sufficient contrast. (1.4.3, 1.4.11)
  • The pointer target meets the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • Opening or selecting an option does not cause an unexpected change of context. (3.2.1, 3.2.2)
  • If the popup filters as the user types, the available results and any no-results message are communicated appropriately. (1.3.1, 4.1.2, 4.1.3)
  • If the combobox popup element is a tree, grid, or dialog, the combobox has an aria-haspopup attribute set to the correct value. The aria-haspopup attribute is not required if the popup element is a listbox. (4.1.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use a native <select> when it provides the required functionality.
  • Use a visible label rather than relying on placeholder text as the only label.
  • Associate an instruction with the input, such as "Suggestions appear as you type."
  • Give the popup a clear visual relationship to the combobox and keep it close to the control.
  • Use aria-expanded to reflect whether the popup is open.
  • Use aria-controls to identify the popup list when the relationship is implemented with ARIA.
  • Use aria-autocomplete="none", list, or both to accurately describe editable autocomplete behavior.
  • Use aria-activedescendant only when focus remains on the combobox while a popup option receives visual or virtual focus.
  • Do not move DOM focus into the listbox unexpectedly if the implemented pattern is designed to keep focus in the text field.
  • Make the selected or active option visually distinguishable without relying on color alone.
  • Provide a clear way to dismiss the popup, such as Escape.
  • Do not automatically select a suggestion on blur unless the behavior is clearly communicated and consistent with the chosen autocomplete pattern.
  • Do not treat arbitrary typed text as a valid value unless the component is intended to accept values that are not in the suggestion list.
  • Do not use aria-haspopup="menu" for a list of selectable values. A combobox generally controls a listbox, not a menu.
  • Do not use a combobox for multiple selections unless the implementation clearly communicates the selected values and uses an appropriate multi-select pattern.
  • Keep option labels stable and sufficiently specific.
  • Provide a useful no-results message when filtering produces no matches.
  • Do not close the popup merely because the pointer moves between the combobox and the popup.
  • Do not make the popup dependent on hover or a drag gesture.

Select-only comboboxes

A select-only combobox does not allow text entry. The user opens a popup and chooses one option from the list. It is functionally similar to a native single-select <select>.

  • The combobox has an accessible name and exposes the collapsed or expanded state. (4.1.2)
  • Opening the popup does not change the current selection. (3.2.2)
  • The current selection is distinguishable from the other options. (1.3.1, 4.1.2)
  • Users can open the popup, move through the options, select an option, and close the popup using the keyboard. (2.1.1)
  • Users can dismiss the popup without changing the selection. (2.1.1)
  • When the popup closes, focus remains on the combobox or returns to another logical location. (2.4.3)
  • The selected value is communicated after selection. (4.1.2)

Typical keyboard behavior

  • Enter or Space opens the popup without changing the current selection.
  • Down Arrow opens the popup or moves through the options according to the implementation.
  • Up Arrow moves through the options according to the implementation.
  • Home and End may move to the first and last options.
  • Enter accepts the active option.
  • Escape closes the popup without changing the selection.

Editable comboboxes

An editable combobox contains a text input. Users may type a value, receive suggestions, and either accept a suggestion or keep the value they entered, depending on the implementation.

  • The text input has an accessible name and exposes the combobox role or equivalent native semantics. (3.3.2, 4.1.2)
  • The input's autocomplete behavior is accurately communicated with aria-autocomplete when the ARIA pattern is used. (4.1.2)
  • Typing does not unexpectedly move focus or erase the user's input. (2.1.1, 3.2.2)
  • The popup opens and filters according to a predictable rule. (3.2.2, 4.1.2)
  • The active suggestion is distinguishable and programmatically exposed. (1.3.1, 4.1.2)
  • Users can accept a suggestion, dismiss the popup, and edit or clear the value. (2.1.1)
  • If arbitrary text is allowed, users can leave the field without selecting a suggestion. (2.1.1, 4.1.2)
  • If only suggested values are valid, invalid or unselected text is identified and explained. (3.3.1, 3.3.3)

Editable autocomplete comboboxes

  • The autocomplete behavior is predictable and is accurately communicated to users. (3.2.2, 4.1.2)
  • Suggestions that appear as the user types are available through the keyboard. (2.1.1)
  • The active suggestion is visually distinguishable and programmatically identified. (1.3.1, 4.1.2)
  • Users can accept a suggestion, dismiss the suggestions, and edit or clear the value. (2.1.1, 4.1.2)
  • If arbitrary text is not allowed, invalid or unselected text is identified and explained. (3.3.1, 3.3.3)
  • If arbitrary text is allowed, valid user-entered text is not incorrectly rejected because it does not match a suggestion. (3.3.1)
  • Any inline completion is distinguishable from text entered by the user. (1.3.1, 4.1.2)

Practical test sequence

Focus Details Applicable Criteria
Identify function
  • Determine what the combobox does.
  • Confirm that combobox is the correct role.
  • Determine what type of combobox it is (e.g., select-only, editable, autocomplete).
  • Determine whether it is a native HTML <select> or a custom combobox.
Semantics and language
  • Confirm that the control is a native <select> when custom behavior is unnecessary, or that the custom control exposes appropriate combobox semantics. (4.1.2)
  • Confirm that the combobox has a visible, descriptive label. (2.4.6, 3.3.2)
  • Confirm that the visible label is included in the accessible name. (2.5.3)
  • Confirm that the popup has the appropriate role, normally listbox, and that its options have appropriate semantics. (1.3.1, 4.1.2)
  • Confirm that the combobox identifies the popup and exposes its expanded state. (1.3.1, 4.1.2)
  • Confirm that the control is not actually a menu button, listbox, checkbox group, or multi-select widget. (1.3.1, 4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 2.4.6 Headings and Labels (Level AA)
  • WCAG 2.2: Understanding SC 2.5.3 Label in Name (Level A)
  • WCAG 2.2: Understanding SC 3.3.2 Labels or Instructions (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Confirm that the control is announced as a combobox or an equivalent native select control. (4.1.2)
  • Verify the accessible name and current value. (3.3.2, 4.1.2)
  • Open the popup and confirm that its expanded state is announced. (4.1.2)
  • Confirm that the popup and its options are identified correctly. (1.3.1, 4.1.2)
  • Move through the options and confirm that the active or selected option is communicated. (4.1.2)
  • Select an option and confirm that the new value is announced or otherwise available when focus returns to the combobox. (4.1.2)
  • For an editable combobox, type characters and confirm that filtering, suggestions, no-results messages, and accepted values are understandable. (1.3.1, 4.1.2, 4.1.3)
  • Confirm that instructions, descriptions, required status, and error messages are available when applicable. (1.3.1, 3.3.1, 3.3.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.2 Labels or Instructions (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
Keyboard only
  • Use Tab and Shift+Tab to move to and away from the combobox. (2.1.1, 2.1.2, 2.4.3)
  • For a select-only combobox, use Enter or Space to open the popup. Confirm that opening it does not change the selection. (2.1.1, 3.2.2)
  • For an editable combobox, type text and confirm that the input remains editable and that suggestions appear according to the documented behavior. (2.1.1, 4.1.2)
  • Use Down Arrow and Up Arrow to move through available options. (2.1.1)
  • Use Enter to accept the active option and confirm that the popup closes appropriately. (2.1.1)
  • Use Escape to dismiss the popup without an unintended selection. (2.1.1)
  • Confirm that focus remains visible and is not completely hidden by the popup or other content. (2.4.7, 2.4.11)
  • Confirm that the popup does not create a keyboard trap. (2.1.2)
  • Confirm that focus moves in a logical order and does not jump unexpectedly when the popup opens or closes. (2.4.3)
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 2.1.2 No Keyboard Trap (Level A)
  • WCAG 2.2: Understanding SC 2.4.3 Focus Order (Level A)
  • WCAG 2.2: Understanding SC 2.4.7 Focus Visible (Level AA)
  • WCAG 2.2: Understanding SC 2.4.11 Focus Not Obscured (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Autocomplete behavior
  • For a no-autocomplete combobox, confirm that typing does not incorrectly suggest that the options have been filtered.
  • For an autocomplete combobox, type characters into the text field and confirm that the availability of suggestions is understandable to screen reader users. The implementation does not necessarily need to announce the number of results after every keystroke, but the popup, options, and active option must be programmatically available.
  • For manual-selection autocomplete, type matching text and confirm that suggestions appear without one being automatically committed.
  • Move through the suggestions with the keyboard and confirm that the active suggestion is visually and programmatically identified and announced by a screen reader.
  • Accept a suggestion and confirm that the input value and selected option update correctly.
  • Dismiss the suggestions with Escape and confirm that the value is not changed unexpectedly.
  • For automatic-selection autocomplete, confirm that the automatically highlighted suggestion is distinguishable and that users can choose a different suggestion.
  • For inline autocomplete, confirm that the completion is visually distinguishable from the user's text and can be accepted, replaced, or rejected.
  • Leave the field without selecting a suggestion and confirm that the resulting behavior is predictable and consistent with the instructions.
  • Enter text that produces no results and confirm that an understandable no-results message is provided to both sighted and screen reader users when needed.
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.3 Error Suggestion (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
Inspect states and relationships
  • Confirm that aria-expanded="false" is used when the popup is closed and aria-expanded="true" when it is open. (4.1.2)
  • Confirm that aria-controls, when used, identifies the correct popup element. (1.3.1, 4.1.2)
  • For an editable combobox, confirm that aria-autocomplete accurately describes the behavior. (4.1.2)
  • When DOM focus remains in the input, confirm that aria-activedescendant, when used, identifies the correct active option. (4.1.2)
  • Confirm that the active option, selected option, and input value do not become inconsistent. (4.1.2)
  • Confirm that filtered results, no-results messages, and loading results are exposed appropriately. (4.1.2, 4.1.3)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
Forms and validation
  • Submit the form without a required value and confirm that the combobox is identified as needing attention. (3.3.1)
  • Confirm that an error message identifies the combobox and explains how to correct the error. (3.3.1, 3.3.3)
  • Confirm that error messages and instructions are programmatically associated with the control. (1.3.1)
  • For restricted-value comboboxes, enter or leave an invalid value and confirm that the result is identified clearly. (3.3.1, 3.3.3)
  • For editable comboboxes that allow arbitrary text, confirm that valid typed text is not incorrectly rejected merely because it was not one of the suggestions. (3.3.1)
  • Confirm that selecting an option does not submit the form or change context unexpectedly. (3.2.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.3 Error Suggestion (Level AA)
Inspect visual aspects
  • Check contrast for the label, input text, popup, options, selected option, active option, borders, icons, and focus indicator. (1.4.3, 1.4.11)
  • Confirm that the selected or active option is not identified by color alone. (1.4.1)
  • Check 200% text resize, a 320-CSS-pixel-wide viewport, and text-spacing overrides. The label, input, popup, options, and error messages must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm that the popup is not clipped by its container or positioned where users cannot reach its options. (1.4.10)
  • Confirm that the input, popup button, and relevant options meet the minimum target size or have sufficient spacing. (2.5.8)
  • Confirm that the popup does not obscure the input or focused option in a way that prevents operation. (2.4.11)
  • Confirm that inline autocomplete text is visually distinguishable from text entered by the user. (1.3.1, 1.4.3)

  • WCAG 2.2: Understanding SC 1.4.3 Contrast (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 1.4.4 Resize Text (Level AA)
  • WCAG 2.2: Understanding SC 1.4.10 Reflow (Level AA)
  • WCAG 2.2: Understanding SC 1.4.11 Non-text Contrast (Level AA)
  • WCAG 2.2: Understanding SC 1.4.12 Text Spacing (Level AA)
