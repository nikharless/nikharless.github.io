Buttons

A button is an interactive control that performs an action when activated. Examples include submitting a form, opening a dialog, expanding content, starting a process, deleting an item, or changing a setting.

Buttons differ from links:

  • Use a button when the action changes the current page, application state, or interface.
  • Use a link when the action navigates to another location or resource.
  • Use a native <button> whenever possible rather than recreating button behavior with a <div>, <span>, or link.

WCAG Requirements

All Buttons

  • The button has a programmatically determinable accessible name that describes its action or purpose. (4.1.2)
  • The control exposes the button role. (4.1.2)
  • The button is operable with a keyboard. (2.1.1)
  • A native button responds to Enter and Space according to its native behavior. A custom button must reproduce equivalent keyboard behavior. (2.1.1)
  • The button's state and properties are programmatically exposed and updated when they change. (4.1.2)
  • The button has a visible focus indicator when it receives keyboard focus. (2.4.7)
  • The button remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.11)
  • The pointer target is at least 24 by 24 CSS pixels, unless a WCAG 2.2 exception applies. (2.5.8)
  • The button is not completely hidden by sticky headers, banners, dialogs, or other author-created content when it receives focus. (2.4.11)
  • The button does not cause an unexpected context change merely because it receives focus. (3.2.1)
  • If activating the button causes a significant context change, the user is informed where appropriate. (3.2.2)
  • If the button is disabled, unavailable, loading, pressed, expanded, or otherwise stateful, that state is communicated visually and programmatically. (4.1.2)
  • A disabled button must not appear operable or respond inconsistently with its disabled state.
  • An icon-only button has an accessible name independent of the icon's appearance. (2.4.6)
  • A button's visible text is included in its accessible name. This is especially important for icon buttons with visible text labels. (2.5.3)
  • Buttons that perform destructive, legal, financial, or data-submission actions provide appropriate error prevention or confirmation where required. (3.3.4)

Command Buttons

A command button performs an action, such as Save, Delete, Print, Add Item, Cancel, Submit, Start or Stop playback.

  • The accessible name identifies the action, such as "Delete report." (2.4.6)
  • The name remains sufficiently specific when several buttons appear together (2.4.6).
  • If the action is asynchronous, the user receives an appropriate status or completion indication. (4.1.3)
  • If activation changes the button's state, the new state is exposed. (4.1.2)
  • A destructive command should identify its consequences and, where applicable, provide confirmation or an undo mechanism. (3.3.4)
  • A button inside a form must have an intentional type. Without an explicit type, a button inside a form may unintentionally submit it. (3.2.2)

Examples

<button type="button">Save changes</button<
<button type="button">Delete project</button<
<button type="submit">Submit application</button>
<button type="button">Cancel</button>

Toggle Buttons

A toggle button switches between two states, such as Bold on/off, Mute/unmute, Show/hide a toolbar, Favorite/unfavorite, Start/stop a mode.

  • The accessible name describes the function, not only the current state. (2.4.6)
  • The current state is exposed with aria-pressed="true" or aria-pressed="false" when using the ARIA toggle-button pattern. (4.1.2)
  • The programmatic state updates at the same time as the visual state. (4.1.2)
  • The pressed state meets minimum contrast requirements. (1.4.3, 1.4.11)
  • The pressed state must be visually distinguishable from the default state when color is ignored. (1.4.1)

Examples

<button type="button" aria-pressed="false">Mute</button>

Disclosure or Expandable Buttons

A disclosure button shows or hides associated content, such as an FAQ answer, filter panel, or additional options.

  • The button identifies the content it controls using aria-controls. (4.1.2)
  • Its expanded state is exposed with aria-expanded="true" or aria-expanded="false". (4.1.2)
  • The expanded state changes when the content opens or closes. (4.1.2)
  • The controlled content is not keyboard-focusable or exposed as available content when it is actually collapsed. (2.4.3)
  • The button remains in a logical position relative to the content it controls. (2.4.3)
  • Focus does not move unexpectedly unless the interaction pattern requires it. (3.2.2)

Example

<button
    type="button"
    aria-expanded="false"
    aria-controls="shipping-details">
    Shipping details
</button>

<div id="shipping-details" hidden>
    ...
</div>

Buttons That Open Dialogs

A dialog-opening button launches a modal or non-modal dialog, such as "Edit profile," "Share," "Delete account," or "Choose date."

  • The button's accessible name describes the dialog or action it opens. (4.1.2)
  • The button visually indicates that it opens a dialog when that is not otherwise clear. WAI-ARIA's APG gives an ellipsis, such as "Save as...," as one common convention.
  • The button programmatically indicates that it opens a dialog using aria-haspopup="dialog". (4.1.2)
  • When the dialog closes, focus returns to the button that opened it, unless a different logical destination is necessary. (2.4.3)

Menu Buttons

A menu button opens a menu of choices or commands. Do not use a menu button for a simple list of ordinary page links unless the interaction genuinely requires a menu pattern.

  • The button communicates that it opens a menu, typically with aria-haspopup="menu" or an equivalent supported implementation. (4.1.2)
  • Its expanded state is communicated with aria-expanded. (4.1.2)
  • The menu opens and closes with Enter and Space. (2.1.1)
  • Keyboard interaction follows the menu-button pattern, including appropriate focus behavior and Escape handling. (2.1.1)
  • Menu items have appropriate roles and keyboard behavior. (4.1.2, 2.1.1)
  • Focus is not lost when the menu opens. (2.4.3)
  • If the menu closes, focus returns to the menu button or another logical location. (2.4.3)

Submit and Reset Buttons

  • The submit button identifies the operation, such as "Place order" or "Search." (2.4.6)
  • A reset action does not occur accidentally when the user intended to submit the form.
  • For legal, financial, or data-modifying submissions, the applicable error-prevention requirements are met. (3.3.4)

Best Practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Prefer native <button> elements.
  • Give every button a visible text label when space and context permit.
  • Use an accessible name that describes the result of activation: "Download invoice" is better than "Download."
  • Keep button labels stable where possible, especially for toggles. Communicate the state separately.
  • Use sentence case and concise action-oriented labels.
  • Do not use an icon alone when the icon's meaning may be ambiguous.
  • Provide a tooltip for an unfamiliar icon, but do not rely on a tooltip as the only accessible name.
  • Use aria-pressed for toggle buttons, aria-expanded for disclosure controls, and aria-haspopup for menu buttons only when those patterns accurately describe the behavior.
  • Do not add ARIA when native HTML already supplies the necessary semantics.
  • Avoid placing multiple adjacent icon-only buttons without sufficient spacing or clear names.
  • Preserve the button's position and accessible name across states unless changing them is necessary.
  • Make loading behavior clear. Prevent duplicate activation where appropriate, but do not remove the accessible name or trap focus unnecessarily.
  • Avoid disabling a button solely because an error exists. When possible, allow activation and explain the validation errors.
  • Ensure hover, active, pressed, disabled, and focus states are visually distinguishable.
  • Keep the entire visible button area clickable, not only the text or icon.
  • Use a confirmation step or undo for destructive actions when accidental activation could cause significant harm.
  • Avoid using a link styled as a button when the control performs an in-page action.
  • Avoid using a button styled as a link when it navigates to another location.
  • A reset button is used only when its behavior is genuinely needed, because clearing entered information can be disruptive.

Practical Test Sequence

Focus Details Applicable Criteria
Identify function
  • Determine what the button does.
  • Confirm that button is the correct role.
  • Determine what type of button it is (e.g., command, toggle, disclosure, menu button, dialog trigger, submit, or reset button).
  • Determine whether it is a native HTML button or a custom button.
Semantics and language
  • Confirm the button is a native <button>, where feasible, or has role="button". It should not have additional roles, contain nested controls, or be nested inside other controls. (4.1.2)
  • Confirm the button has an accessible name that describes its action and includes any visible label text. (4.1.2, 2.4.6, 2.5.3)
  • If the button appears across multiple pages, confirm that it is identified consistently. (3.2.4)
  • If the button is inside a form, confirm it has an explicit type. (3.2.2)
  • Confirm that any referenced IDs are valid.

  • WCAG 2.2: Understanding SC 2.4.6 Headings and Labels (Level AA)
  • WCAG 2.2: Understanding SC 2.5.3 Label in Name (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
  • WCAG 2.2: Understanding SC 3.2.4 Consistent Identification (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Confirm the button is identified as a button. (4.1.2)
  • Verify a meaningful name. Visible labels must be included in the accessible name. Decorative icons should not be read. (4.1.2, 2.5.3, 1.1.1)
  • Verify pressed, disabled, expanded, or popup states are communicated when applicable. (4.1.2)
  • If multiple buttons have the same visible label, verify that the accessible name is unambiguous. (2.4.6)
  • Confirm that the button and any content that it controls are read in a meaningful order. (1.3.2)
  • Confirm any status messages are read when the button is activated. There should always be feedback when an action is performed. (4.1.3)

Keyboard only
  • Use Tab and Shift+Tab to focus and unfocus the button. Use Enter and Space to activate it. Keyboard activation should perform the same function as a mouse click. The page should not scroll unexpectedly when Space is used to activate the button. Disabled buttons should not be activatable. (2.1.1, 2.1.2)
  • Confirm that the button has a visible focus indicator. (2.4.7)
  • Confirm that the button appears in a logical focus order. Check the focus order of any additional content, such as menus or expanded regions, that is controlled by the button. (2.4.3)
  • If the button exposes additional content, confirm that it does not completely obscure the focus of other controls. (2.4.11)
  • Confirm that no unexpected context changes occur when the button is focused or activated. Focus should not be removed or moved on activation, unless the button's purpose requires it. Only submit buttons may submit forms. (3.2.1, 3.2.2)

Visual presentation
  • Check contrast for text and icons in all states (focus, active, pressed). Check contrast for the focus indicator. (1.4.3, 1.4.11)
  • Confirm states are not conveyed by color alone. (1.4.1)
  • Check 200% text resize, 320-CSS-pixel-wide viewport, and text spacing overides. The button and any controlled content must remain visible, unclipped, unobscured, and usable. Horizontal scrolling should not be required. (1.4.4, 1.4.10, 1.4.12)
  • Confirm target size or sufficient spacing. (2.5.8)
