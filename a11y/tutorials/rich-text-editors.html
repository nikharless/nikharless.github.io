Rich text editors

A rich text editor is an editable region that allows users to enter, edit, and format text. Depending on the implementation, it may support headings, paragraphs, lists, links, images, tables, quotations, code blocks, text formatting, alignment, color, comments, or other structured content.

A rich text editor may include one or more formatting toolbars. Each formatting toolbar must also meet the applicable requirements in the Toolbars checklist. This document covers editor-specific requirements, including the editable area, selection, formatting feedback, dialogs, and interactions between the editor and its controls.

Rich text editors differ from related controls:

  • Use a rich text editor when users must create or edit formatted, structured content.
  • Use a native <textarea> when users only need to enter unformatted multiline text.
  • Use a plain-text or code editor when users need to write source code, Markdown, or other structured plain text rather than visually formatted content.
  • Use a read-only document viewer when users can read formatted content but cannot edit it.
  • Do not use a rich text editor merely to display formatted content.
  • Use native semantic content and browser editing behavior where possible rather than recreating text editing, caret movement, selection, and clipboard behavior with custom scripting.

WCAG requirements

  • The editable region has a programmatically determinable accessible name that identifies its purpose, such as "Message", "Article body", or "Comment". (3.3.2, 4.1.2)
  • The visible label is included in the accessible name of the editable region. (2.5.3)
  • The editable region exposes appropriate editable text-input semantics. A custom multiline editor typically exposes role="textbox" and aria-multiline="true". (4.1.2)
  • The editable, read-only, disabled, required, invalid, and other relevant states of the editing region are programmatically determinable and update when they change. (4.1.2)
  • Instructions, descriptions, required status, character limits, formatting restrictions, and validation errors are programmatically associated with the editable region when applicable. (1.3.1, 3.3.1, 3.3.2, 4.1.2)
  • The editor supports keyboard text entry, caret movement, text selection, editing, and deletion without requiring a pointer. (2.1.1)
  • Keyboard focus moves to, through, and away from the editor in a logical order. (2.4.3)
  • If Tab or Shift+Tab is used to edit, indent, outdent, or otherwise modify editor content, users can move focus away from the editor using a keyboard method. If the exit method requires keys other than standard Tab or Shift+Tab, instructions identify the method for leaving the editor. (2.1.2, 3.3.2)
  • The editor has a visible focus indicator when it receives keyboard focus. (2.4.7)
  • The focused editing region, selected text, caret, and focused controls are not completely hidden by author-created content. (2.4.11)
  • When the editor includes formatting toolbars, each toolbar meets the applicable requirements in the Toolbar checklist, including keyboard operation, focus management, names, roles, states, and values. (2.1.1, 2.4.3, 4.1.2)
  • Users can determine which editing region is affected by associated formatting controls, especially when more than one editor is present on a page. (1.3.1, 4.1.2)
  • Formatting controls expose their current state or value when applicable, such as pressed/not pressed, selected/unselected, checked/unchecked, expanded/collapsed, or current value. (4.1.2)
  • When a formatting action changes selected text or the active insertion state, the visible result and programmatically exposed control state remain synchronized. (1.3.1, 4.1.2)
  • Using a formatting control does not unexpectedly discard the user's text selection or move focus to an illogical location. (2.4.3, 3.2.2)
  • Dialogs, menus, comboboxes, color pickers, upload controls, tables, and other components opened from the editor meet the applicable requirements for those components. (2.1.1, 2.4.3, 4.1.2)
  • Editor status changes and errors that are presented without moving focus are programmatically determinable when users need that information. (4.1.3)
  • Text, formatting states, controls, focus indicators, selection indicators, and error messages are not conveyed by color alone. (1.4.1)
  • Editor text, control labels, icons, formatting indicators, boundaries needed to identify controls, and focus indicators have sufficient contrast. (1.4.3, 1.4.11)
  • The editor remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • Toolbar controls, editor actions, dialogs, upload controls, and other relevant pointer targets meet the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • Moving focus into the editor, through text, or to formatting controls does not cause an unexpected change of context. (3.2.1)
  • Formatting, inserting, deleting, pasting, uploading, or saving content does not cause an unexpected change of context unless the result is clearly communicated and appropriate. (3.2.2)

Editable regions

The editable region is the central text-entry surface of a rich text editor. It may be implemented with contenteditable="true", an editable iframe document, or another editing technology.

  • The editable region has an accessible name that identifies the content users are expected to create or edit. (3.3.2, 4.1.2)
  • A multiline editable region exposes multiline text-input semantics. (4.1.2)
  • The editor's editable, read-only, disabled, required, and invalid states are programmatically determinable where applicable. (4.1.2)
  • Users can enter, edit, select, copy, cut, paste, and delete text with a keyboard when those functions are supported. (2.1.1)
  • Enter creates a line break or paragraph according to the editor's documented behavior and does not unexpectedly submit the surrounding form. (2.1.1, 3.2.2)
  • Text selection and the insertion caret remain visible or otherwise discernible while users edit content. (2.4.7, 2.4.11)
  • The editor's programmatic content, reading order, and visual presentation remain synchronized after users enter or edit content. (1.3.1, 1.3.2)
  • If the editor has a character, word, or content limit, the limit and remaining/used amount are available to users when needed. (1.3.1, 3.3.2, 4.1.3)

Formatting toolbars

A rich text editor may provide one or more formatting toolbars with controls for commands such as bold, italic, headings, lists, alignment, links, images, colors, tables, undo, and redo.

  • Each editor toolbar meets the applicable requirements in the Toolbars checklist. (2.1.1, 2.4.3, 4.1.2)
  • The relationship between the toolbar and the editing region it controls is understandable to users. (1.3.1, 4.1.2)
  • Formatting command controls have accessible names that describe their actions, such as "Bold", "Insert link", or "Numbered list". (2.4.6, 4.1.2)
  • Toggle formatting controls expose their active state, such as aria-pressed="true" or aria-pressed="false", when the control follows the toggle-button pattern. (4.1.2)
  • Controls that select a text style, heading level, font, paragraph alignment, or another value expose the current selected value. (4.1.2)
  • When the caret moves into differently formatted content, associated control states and values update accurately. (4.1.2)
  • Using a formatting control applies the intended result to the selected text or current insertion point without unexpectedly discarding the selection. (2.4.3, 3.2.2)
  • Formatting state is not conveyed by color alone. (1.4.1)

Links, images, and media

Rich text editors often include dialogs or popups for inserting and editing links, images, files, media, and other embedded content.

  • A link-insertion dialog identifies the target URL, link text, and any other required information with labeled controls and instructions. (1.3.1, 3.3.2, 4.1.2)
  • When images or other non-text content can be inserted, users can provide appropriate text alternatives or identify the content as decorative. (1.1.1)
  • Image alternative-text fields have clear labels and instructions. (3.3.2, 4.1.2)
  • File and image upload controls are keyboard-operable and have meaningful accessible names. (2.1.1, 4.1.2)
  • If the editor supports dropping files or media, an alternative method of selecting and inserting them is available without dragging. (2.5.7)
  • Upload progress, completion, failure, and validation messages are available to assistive technology. (3.3.1, 4.1.3)
  • After inserting, editing, or removing an embedded object, focus returns to a logical location and users can determine the result. (2.4.3, 4.1.3)

Tables and structured content

Some rich text editors allow users to insert and edit tables, headings, lists, quotations, code blocks, and other structured content.

  • Users can create and edit headings, lists, tables, and other structures without relying solely on visual formatting. (1.3.1)
  • When the editor creates a heading, list, table, or other structure, the resulting content exposes appropriate native HTML or equivalent semantics. (1.3.1)
  • Table-creation and table-editing controls are keyboard-operable. (2.1.1)
  • Users can identify and operate table rows, columns, cells, headers, and table actions when the editor provides those functions. (1.3.1, 4.1.2)
  • Controls that insert or alter structured content have meaningful names and communicate relevant states or values. (4.1.2)
  • When a structure is added, changed, or removed, users can determine the resulting content and location. (1.3.1, 4.1.3)

Editor dialogs and popups

Formatting commands may open dialogs, menus, comboboxes, color pickers, table pickers, link editors, find-and-replace interfaces, or other popups.

  • Dialogs opened from the editor meet the applicable requirements in the Modal dialogs checklist. (2.1.1, 2.1.2, 2.4.3, 4.1.2)
  • Menus opened from the editor meet the applicable requirements for menu buttons and menus. (2.1.1, 2.4.3, 4.1.2)
  • Style, font, heading, color, and other value-selection controls meet the applicable requirements for comboboxes, listboxes, radio groups, or other implemented patterns. (2.1.1, 4.1.2)
  • When a dialog or popup closes, focus returns to the invoking editor control or another logical editing location. (2.4.3)
  • Opening and closing a dialog or popup does not unexpectedly discard selected text, editor content, or unsaved changes. (3.2.2)
  • Editor dialogs identify errors, provide known correction suggestions, and associate messages with affected fields. (1.3.1, 3.3.1, 3.3.3, 4.1.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Provide a visible label and concise instructions before the editor.
  • Use a native <textarea> when rich formatting is not genuinely needed.
  • Use a native or established editing surface, such as contenteditable="true", rather than attempting to recreate ordinary text editing with canvas or custom pointer-only behavior.
  • Use role="textbox" and aria-multiline="true" for a custom multiline editable region when those semantics are not provided natively.
  • Do not add role="application" to the entire editor or page as a default implementation technique. Use it only when a carefully tested interaction model requires it.
  • Provide a visible indication when the editor is read-only, disabled, empty, required, invalid, saving, or has unsaved changes.
  • Keep the editor's accessible name stable. Do not replace the field name with its current formatting state, character count, or status message.
  • Provide a visible formatting toolbar only for commands that users need. Avoid overwhelming users with unnecessary controls.
  • Use familiar text labels or familiar icons with accessible names for formatting commands.
  • Do not rely on tooltips as the only accessible name for icon-only formatting controls.
  • Preserve selected text when a user invokes a formatting control, except when selection loss is necessary and clearly communicated.
  • Return focus to a logical editing location after a formatting dialog, menu, color picker, link editor, image picker, or other popup closes.
  • Provide ordinary text-entry and editing behavior, including caret movement, selection, copy, cut, paste, undo, and redo, when those actions are supported.
  • Allow users to paste content without requiring pointer interaction.
  • When pasted content is modified, stripped, rejected, or converted, provide understandable feedback.
  • Provide persistent, field-specific validation errors rather than relying only on a temporary toast or a color change.
  • Provide an accessible source/HTML/Markdown mode when one is offered, and clearly identify which editing mode is active.
  • Provide a keyboard-operable alternative for inserting or arranging images, files, media, tables, or other embedded objects.
  • Provide an undo mechanism or confirmation for consequential deletion or substantial content changes when appropriate.
  • When multiple editors are present, clearly identify each editor and its associated toolbar, status information, and validation messages.
  • Prefer standard Tab and Shift+Tab navigation when indentation is not essential.
  • When Tab inserts indentation, provide a clear, consistent keyboard method for leaving the editor, such as leaving editing mode with Escape and then using Tab or Shift+Tab.
  • Place exit instructions near the editor and programmatically associate them with the editing region.
  • Use contenteditable="true" when using role="textbox", even if aria-readonly="true" is set. This communicates that the content would be editable if it were not read-only.

Notes

Keyboard trap

Pass:

  1. The editor uses Tab to indent.
  2. A visible instruction says: "Press Escape, then Tab to move to the next control."
  3. The instruction is associated with the editor.
  4. After Escape, Tab moves to the next control; Shift+Tab moves to the preceding control.

Fail:

  1. The editor uses Tab to insert indentation and Shift+Tab to outdent.
  2. There is no keyboard command to move focus out, or no instruction describes it.
