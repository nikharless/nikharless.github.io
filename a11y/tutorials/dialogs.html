Modal dialogs

A modal dialog is a window that appears above the page and temporarily prevents users from interacting with the content behind it. A modal dialog may contain information, form controls, confirmation actions, or another interactive task.

Modal dialogs differ from non-modal dialogs:

  • A modal dialog prevents interaction with the rest of the page until it is closed.
  • A non-modal dialog allows users to continue interacting with the rest of the page.
  • Use an alert dialog for a brief, important message that requires the user's immediate attention, such as a confirmation of a potentially destructive action.
  • Use a separate dialog pattern for the dialog itself. The button or link that opens the dialog is tested both as a trigger and as part of the dialog's focus-management behavior.

WCAG requirements

  • The dialog has an accessible name, usually provided by a visible heading referenced with aria-labelledby. (4.1.2)
  • The dialog exposes the dialog role. A native <dialog> provides dialog semantics, while a custom implementation may use role="dialog". (4.1.2)
  • A modal dialog exposes its modal state appropriately and prevents interaction with the page behind it. (4.1.2)
  • When the modal opens, focus moves into the dialog. (2.4.3)
  • Keyboard focus remains within the modal dialog while it is open. (2.1.1, 2.1.2, 2.4.3)
  • Users can close the modal dialog with a keyboard-operable control. (2.1.1)
  • When supported by the design, Escape closes the modal dialog. (2.1.1)
  • When the dialog closes, focus returns to the control that opened it, unless another logical destination is necessary. (2.4.3)
  • All controls within the dialog have accessible names, appropriate roles, and programmatically determinable states and values. (4.1.2)
  • The dialog and its controls have a logical focus order. (2.4.3)
  • The dialog does not create a keyboard trap from which users cannot exit using a standard keyboard interaction. (2.1.2)
  • Keyboard focus is visible and is not completely hidden by other content. (2.4.7, 2.4.11)
  • The dialog title, text, controls, and focus indicators have sufficient contrast. (1.4.3, 1.4.11)
  • The dialog remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • The dialog does not cause an unexpected change of context merely because it receives focus. (3.2.1)
  • The control that opens the dialog has a meaningful accessible name that describes the dialog or action. (2.4.6, 4.1.2)
  • If the dialog contains a form, its fields, instructions, validation errors, and submission behavior meet the applicable form requirements. (1.3.1, 3.3.1, 3.3.2, 3.3.3, 4.1.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Prefer the native <dialog> element and showModal() when they provide the required behavior.
  • Give every dialog a visible heading whenever possible.
  • Use aria-labelledby to associate the dialog with its visible heading.
  • Use aria-describedby for a short description when users need additional context.
  • Use aria-modal="true" only when the dialog is genuinely modal and the background is actually inert.
  • Do not use aria-hidden="true" on the background as a substitute for making it non-interactive. The page behind a modal must not be reachable by keyboard or pointer.
  • Move focus to the first meaningful control, the dialog heading, or another carefully chosen element when the dialog opens. Do not always place focus on the close button.
  • Place initial focus on a heading or static text when users need to read substantial introductory content before choosing an action.
  • Provide a clearly labeled close button inside the dialog.
  • Allow users to close the dialog with Escape unless there is a strong reason not to.
  • Return focus to the invoking control when the dialog closes.
  • If the invoking control no longer exists, return focus to the most logical available destination.
  • Do not allow interaction with content behind a modal dialog.
  • Do not move focus to the backdrop or to an element behind the dialog.
  • Keep the dialog within the viewport or provide a usable way to scroll its content without losing access to the title and controls.
  • Do not close the dialog merely because the pointer moves outside it.
  • Use a confirmation dialog for destructive actions only when confirmation provides meaningful protection against accidental activation.
  • Use an alert dialog sparingly. Do not use it for ordinary informational content that does not require immediate attention.
  • Make the primary and secondary actions clear, especially when one action is destructive.
  • Do not change the dialog's purpose or accessible name without communicating the change.

Modal dialog types

Informational dialogs

An informational dialog presents additional text, instructions, or details. It should have a meaningful title and an operable way to close it.

  • Confirm that the dialog title identifies its subject. (4.1.2)
  • Confirm that initial focus is placed where users can begin reading or operating the dialog. (2.4.3)
  • Confirm that the dialog can be closed with its close button and, where supported, Escape. (2.1.1)
  • Confirm that focus returns to the invoking control when the dialog closes. (2.4.3)

Form dialogs

A form dialog contains inputs or other controls that allow users to complete a task, such as editing a profile or adding an address.

  • Confirm that every form control has a visible label and an accessible name. (1.3.1, 3.3.2, 4.1.2)
  • Confirm that the dialog provides instructions needed to complete the form. (3.3.2)
  • Confirm that validation errors identify the affected fields and explain how to correct them. (3.3.1, 3.3.3)
  • Confirm that users can reach and operate every form control with the keyboard. (2.1.1)
  • Confirm that submitting or cancelling the form has predictable results. (3.2.2)
  • Confirm that focus is managed appropriately after successful submission, validation failure, or cancellation. (2.4.3)

Confirmation dialogs

A confirmation dialog asks the user to confirm an action, often before deleting, submitting, or changing important information.

  • Confirm that the dialog clearly identifies the action being confirmed. (2.4.6, 4.1.2)
  • Confirm that the consequences of the action are understandable. (3.3.2)
  • Confirm that the least destructive or safest action is not obscured or made difficult to reach.
  • For legal, financial, or data-related submissions, confirm that the applicable error-prevention requirements are met. (3.3.4)
  • Confirm that cancelling or closing the dialog does not perform the action. (3.2.2)

Alert dialogs

An alert dialog is a special type of dialog used for a brief, important message that requires the user's immediate attention. It should not be used for every modal message.

  • Confirm that the alert dialog uses role="alertdialog" only when the message requires immediate attention. (4.1.2)
  • Confirm that the alert dialog has an accessible name and, when appropriate, an accessible description. (4.1.2)
  • Confirm that initial focus is placed on an appropriate element, such as the least destructive action or the alert text. (2.4.3)
  • Confirm that the alert dialog can be dismissed or resolved with the keyboard. (2.1.1, 2.1.2)
  • Confirm that the alert dialog does not allow interaction with the page behind it. (2.1.2, 4.1.2)

Practical test sequence

Focus Details Applicable Criteria
Semantics and language
  • Confirm that the modal uses a native <dialog> or exposes role="dialog". (4.1.2)
  • Confirm that the dialog has an accessible name, preferably from a visible heading referenced with aria-labelledby. (4.1.2)
  • Confirm that a short description is associated with the dialog when additional context is needed. (1.3.1, 4.1.2)
  • Confirm that a genuinely modal dialog exposes its modal state appropriately. (4.1.2)
  • Confirm that the control that opens the dialog has a meaningful accessible name. (2.4.6, 4.1.2)
  • Confirm that the close control is a native button or otherwise exposes the correct button semantics. (4.1.2)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 2.4.6 Headings and Labels (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Open the dialog and confirm that the dialog role, accessible name, and modal state are announced or otherwise available. (4.1.2)
  • Confirm that the dialog title is meaningful and that the dialog description is available when provided. (4.1.2)
  • Confirm that controls within the dialog have meaningful names, roles, and states. (4.1.2)
  • Confirm that background content is not presented as available for interaction while the modal is open. (4.1.2)
  • Confirm that validation messages, status messages, and errors within the dialog are available when applicable. (3.3.1, 4.1.3)
  • Close and reopen the dialog and confirm that its name, state, and initial focus behavior remain consistent. (3.2.4, 4.1.2)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Keyboard only
  • Use Tab to open the modal and confirm that focus moves into the dialog. (2.1.1, 2.4.3)
  • Use Tab and Shift+Tab to move through the dialog. Focus must not move to the page behind the modal. (2.1.2, 2.4.3)
  • From the last focusable element, press Tab and confirm that focus moves to the first focusable element in the dialog. From the first element, press Shift+Tab and confirm that focus moves to the last. (2.1.2, 2.4.3)
  • Activate the close button with the keyboard. (2.1.1)
  • Press Escape and confirm that the dialog closes when this behavior is supported. (2.1.1)
  • Confirm that focus is visible on every focusable element and is not completely hidden by the dialog or other content. (2.4.7, 2.4.11)
  • Close the dialog and confirm that focus returns to the control that opened it or another logical destination. (2.4.3)
  • Confirm that the modal does not create a trap from which users cannot exit using the close control or another standard method. (2.1.2)
  • WCAG 2.2: Understanding SC 2.1.1 Keyboard (Level A)
  • WCAG 2.2: Understanding SC 2.1.2 No Keyboard Trap (Level A)
  • WCAG 2.2: Understanding SC 2.4.3 Focus Order (Level A)
  • WCAG 2.2: Understanding SC 2.4.7 Focus Visible (Level AA)
  • WCAG 2.2: Understanding SC 2.4.11 Focus Not Obscured (Minimum) (Level AA)
Pointer and touch
  • Open and close the modal with a pointer and touch input where applicable. (2.1.1, 2.5.1)
  • Confirm that the close button and other controls have adequate target size and spacing. (2.5.8)
  • Confirm that clicking or tapping the backdrop does not accidentally perform the dialog's primary or destructive action.
  • If clicking the backdrop closes the dialog, confirm that the behavior is consistent and does not cause accidental data loss.
  • Confirm that touch users can complete the dialog without requiring a complex gesture. (2.5.1)
  • WCAG 2.2: Understanding SC 2.5.1 Pointer Gestures (Level A)
  • WCAG 2.2: Understanding SC 2.5.8 Target Size (Minimum) (Level AA)
Forms and validation
  • Submit the dialog form with valid data and confirm that the expected result occurs. (2.1.1, 3.2.2)
  • Submit the form with invalid or missing data and confirm that errors identify the affected fields. (3.3.1)
  • Confirm that error messages explain how to correct the problem when a correction is known. (3.3.3)
  • Confirm that errors and instructions are programmatically associated with the relevant fields. (1.3.1, 4.1.2)
  • Confirm that focus is managed appropriately after a validation failure. (2.4.3)
  • Confirm that cancelling the form does not submit it or unexpectedly discard important data. (3.2.2, 3.3.4)
  • For legal, financial, or data-related submissions, confirm that users can review, correct, or reverse the submission as applicable. (3.3.4)
  • WCAG 2.2: Understanding SC 1.3.1 Info and Relationships (Level A)
  • WCAG 2.2: Understanding SC 3.3.1 Error Identification (Level A)
  • WCAG 2.2: Understanding SC 3.3.3 Error Suggestion (Level AA)
  • WCAG 2.2: Understanding SC 3.3.4 Error Prevention (Legal, Financial, Data) (Level AA)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Inspect visual aspects
  • Check contrast for the dialog background, text, buttons, icons, borders, backdrop, and focus indicators. (1.4.3, 1.4.11)
  • Confirm that the dialog is visually distinguishable from the page behind it. (1.4.11)
  • Check 200% text resize, a 320-CSS-pixel-wide viewport, and text-spacing overrides. The dialog title, content, controls, and close button must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm that dialog content can be scrolled without making the title, close button, or focused control inaccessible. (1.4.10)
  • Confirm that the close button and other controls meet the minimum target size or have sufficient spacing. (2.5.8)
  • Confirm that focused controls are not obscured by the dialog, sticky content, or other author-created content. (2.4.7, 2.4.11)
  • Confirm that state and purpose are not conveyed by color alone. (1.4.1)
  • WCAG 2.2: Understanding SC 1.4.1 Use of Color (Level A)
  • WCAG 2.2: Understanding SC 1.4.3 Contrast (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 1.4.4 Resize Text (Level AA)
  • WCAG 2.2: Understanding SC 1.4.10 Reflow (Level AA)
  • WCAG 2.2: Understanding SC 1.4.11 Non-text Contrast (Level AA)
  • WCAG 2.2: Understanding SC 1.4.12 Text Spacing (Level AA)
  • WCAG 2.2: Understanding SC 2.5.8 Target Size (Minimum) (Level AA)
