Switches

A switch is a two-state control that represents whether a setting, feature, or service is on or off. Selecting a switch generally takes effect immediately.

Switches differ from other controls:

  • Use a switch when users can immediately turn a single setting or service on or off.
  • Use a checkbox when users select or deselect an option, especially when selections are submitted together as part of a form.
  • Use a radio group when users must choose one option from a group of mutually exclusive choices.
  • Use a toggle button when users turn a mode, tool, or command state on or off.
  • Use a disclosure button when the control shows or hides associated content rather than changing an on/off setting.
  • Use a native <input type="checkbox"> with role="switch" whenever possible when a switch presentation is required.

WCAG requirements

  • Each switch has a programmatically determinable accessible name. (4.1.2)
  • The control exposes switch semantics. A native <input type="checkbox" role="switch"> or custom element with role="switch" provides switch semantics. (4.1.2)
  • The switch exposes aria-checked="false" when off and aria-checked="true" when on. For a native checkbox with role="switch", the native checked state is exposed automatically. (4.1.2)
  • The switch state is programmatically determinable and updates when the state changes. (4.1.2)
  • A switch does not use aria-checked="mixed". Switches have only on and off states. (4.1.2)
  • Each switch has a visible label that identifies the setting, feature, or service it controls and is associated with it programmatically. (1.3.1, 3.3.2)
  • The visible label is included in the switch's accessible name. (2.5.3)
  • The switch is operable with a keyboard. (2.1.1)
  • The switch can be reached and operated in a logical focus order. (2.4.3)
  • The switch has a visible focus indicator when it receives keyboard focus. (2.4.7)
  • The on and off states are not conveyed by color alone. (1.4.1)
  • The switch label, state indicator, and focus indicator have sufficient contrast. (1.4.3, 1.4.11)
  • The switch remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • The pointer target meets the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • A switch that is disabled or unavailable exposes that state programmatically and does not respond as an available switch. (4.1.2)
  • If a group of switches has a common purpose, the group has an appropriate programmatic label. (1.3.1, 2.4.6)
  • If a switch controls another part of the interface, the relationship and resulting state are programmatically determinable. (1.3.1, 4.1.2)
  • If the switch affects a required form setting or preference, relevant instructions and validation errors are communicated to users. (1.3.1, 3.3.1, 3.3.2, 4.1.2)
  • Changing a switch state does not cause an unexpected change of context. (3.2.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use a native <input type="checkbox" role="switch"> with an associated <label> whenever possible.
  • Use a concise, stable label that names the setting or service, such as Dark mode, Notifications, or Auto-play videos.
  • Do not change the accessible name between states, such as changing Enable notifications to Disable notifications. The label identifies the setting; the on/off state communicates its current value.
  • Make the visible label clickable in addition to the switch itself.
  • Make the entire switch and label area an adequate activation target.
  • Provide a visible text or graphic indication of the on and off states in addition to a color change, such as On/Off, a changed thumb position, or a state icon.
  • If visible text indicates the state, hide duplicate On and Off text from assistive technology when the switch role and state already communicate it.
  • Use a fieldset and legend when a related group of switches has a common question or purpose.
  • Do not use a switch when the change should be reviewed, submitted, or confirmed with other form values before taking effect.
  • Do not use a switch for a selection that supports a mixed or partially selected state. Use a checkbox when a mixed state is meaningful.
  • Do not use aria-checked directly on a native checkbox with role="switch". The browser maps the checked state automatically.
  • Make immediate effects clear. If a switch starts, stops, exposes, removes, or changes significant content, provide appropriate feedback without moving focus unexpectedly.
  • Ensure on, off, disabled, hover, and focus states are visually distinguishable.
  • Do not use a switch solely as a visual style for a button, checkbox, disclosure, or another control with different semantics.
