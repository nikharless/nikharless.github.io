Tree views

A tree view is a hierarchical widget that presents related items as nested nodes. Users can move through visible nodes, expand or collapse parent nodes, and, depending on the implementation, select or activate individual nodes.

Tree views differ from other controls:

  • Use a tree view when users need to browse or operate a hierarchy, such as folders and files, nested categories, a site structure, or organizational items.
  • Use an ordinary nested list of links or disclosures when the content is primarily page navigation and a full tree-view keyboard model is unnecessary.
  • Use an accordion when related sections are stacked vertically and users may need to view multiple expanded sections at the same time.
  • Use a listbox when users select options from a flat list rather than navigate a hierarchy.
  • Use a menu or menu button for a list of commands, not for a hierarchical collection of selectable or navigable content.
  • Use a native list structure where possible, and apply the tree-view pattern only when the specialized tree behavior is needed.

WCAG requirements

  • The tree container exposes role="tree". (4.1.2)
  • Each node exposes role="treeitem". (4.1.2)
  • Each nested group of child nodes exposes role="group". (1.3.1, 4.1.2)
  • The tree has a programmatically determinable accessible name that identifies its purpose. (1.3.1, 2.4.6, 4.1.2)
  • Each tree item has a programmatically determinable accessible name that identifies the node. (4.1.2)
  • A tree item that has child nodes exposes aria-expanded="false" when collapsed and aria-expanded="true" when expanded. Leaf nodes do not expose aria-expanded. (4.1.2)
  • When hierarchy information is not computable from the DOM structure, tree items expose aria-level, aria-posinset, and aria-setsize as needed to communicate their depth and position within the hierarchy. (1.3.1, 4.1.2)
  • If the tree supports selection, the selected state is programmatically determinable and updates when selection changes. (4.1.2)
  • In a single-select tree, selection behavior is clear and no more than one node is selected at a time. (1.3.1, 4.1.2)
  • In a multi-select tree, each selectable item exposes its selected or unselected state, and users can determine which items are selected. (4.1.2)
  • The tree is operable using a keyboard. (2.1.1)
  • Keyboard focus moves through visible tree items in a logical order and does not enter collapsed child nodes. (2.4.3)
  • The focused tree item has a visible focus indicator. (2.4.7)
  • Focused tree items are not completely hidden by sticky headers, banners, dialogs, or other author-created content. (2.4.11)
  • Expanded/collapsed, selected/unselected, and current-item states are not conveyed by color alone. (1.4.1)
  • Tree-item text, state indicators, icons needed to understand a node, and focus indicators have sufficient contrast. (1.4.3, 1.4.11)
  • The tree remains usable when text is enlarged, spacing is increased, or the viewport is narrow. (1.4.4, 1.4.10, 1.4.12)
  • Tree items and their expand/collapse controls meet the minimum target-size requirement or an applicable exception applies. (2.5.8)
  • A disabled or unavailable tree item exposes that state programmatically and cannot be operated as though it were available. (4.1.2)
  • Moving focus through the tree does not cause an unexpected change of context. (3.2.1)
  • Activating a tree item does not cause an unexpected change of context unless the node's purpose and resulting behavior are understandable. (3.2.2)

Selection trees

A selection tree allows users to choose one or more nodes. Selection is separate from keyboard focus unless the implementation intentionally uses selection-follows-focus behavior.

Single-select trees

  • Only one item is selected at a time. (1.3.1, 4.1.2)
  • The selected item exposes aria-selected="true". (4.1.2)
  • When selection does not follow focus, moving focus does not change the selected item. (2.4.3, 3.2.1)
  • When selection follows focus, the selection state updates consistently as focus moves. (4.1.2)

Multi-select trees

  • Each selectable tree item exposes aria-selected="true" when selected and aria-selected="false" when selectable but unselected. (4.1.2)
  • Users can select and deselect items using the documented keyboard interaction. (2.1.1)
  • Selection changes do not unexpectedly move focus, navigate away, or cause another unexpected context change. (2.4.3, 3.2.2)
  • Multiple selected items are visually distinguishable without relying on color alone. (1.4.1, 1.4.11)

Navigation trees

A navigation tree organizes links or locations hierarchically. Activating a node may navigate to a page, reveal a section, or move focus to content in the same interface.

  • Each navigable tree item or link has a meaningful name that identifies its destination. (2.4.4, 4.1.2)
  • Current-page or current-location information is programmatically determinable when it is conveyed visually. (1.3.1, 4.1.2)
  • Activating a navigation node moves users to the expected destination. (2.4.4)
  • If activation loads new content without a full page refresh, focus moves to the newly displayed content or another logical location. (2.4.3)
  • Expanding and collapsing a branch remains distinct from navigating to the node's destination when both actions are available. (1.3.1, 2.1.1, 4.1.2)

Best practices

These practices improve usability and robustness, although not all are separate WCAG requirements in every implementation.

  • Use the tree-view pattern only when a hierarchy and specialized arrow-key navigation genuinely benefit users.
  • Give the tree a visible heading or label that identifies its purpose, such as "File browser", "Product categories", or "Documentation navigation".
  • Use concise, meaningful names for nodes.
  • Distinguish parent nodes from leaf nodes visually, such as with a chevron or folder icon, but do not rely on the visual indicator alone.
  • Use a clear visual indication of expanded and collapsed states, such as changed chevron direction, plus/minus symbols, or another non-color cue.
  • Keep focus and selection visually distinguishable. A focused item is not necessarily selected, and a selected item is not necessarily focused.
  • Keep selection behavior stable. Do not automatically select a node merely because it receives focus unless the component explicitly uses selection-follows-focus behavior.
  • Use a consistent rule for node activation, such as opening a file, navigating to a page, or selecting an item.
  • Do not automatically navigate to another page merely because focus moves to a tree item.
  • Make the full visible row or a clearly defined control area operable, rather than requiring users to target a small chevron precisely.
  • Ensure users can distinguish the expand/collapse control from the node's activation control when those actions are separate.
  • Do not hide the current page or current item inside a collapsed branch when users need to identify their current location.
  • For dynamically loaded or virtualized trees, expose loading, error, and completion status to assistive technology.
  • For trees with many nodes, support type-ahead navigation by initial characters.
  • Use a simpler list, nested navigation, or disclosure pattern when the full arrow-key tree model would add unnecessary complexity.

Practical test sequence

Focus Details Applicable Criteria
Identify function
  • Confirm that tree is the correct pattern and that the component represents a hierarchy rather than a flat list, menu, accordion, listbox, or ordinary navigation list. (1.3.1, 4.1.2)
  • Determine whether the tree is used for navigation, single selection, multiple selection, file/folder management, or another purpose.
  • Determine whether selection follows focus or requires a separate selection action.
  • Determine whether parent nodes can be expanded and collapsed, whether nodes can be activated, and whether those are separate actions.
  • Determine whether the tree is fully rendered in the DOM, dynamically loaded, or virtualized.

  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Semantics and language
  • Confirm that the container exposes role="tree". (4.1.2)
  • Confirm that each node exposes role="treeitem". (4.1.2)
  • Confirm that child-node containers expose role="group". (1.3.1, 4.1.2)
  • Confirm that the tree has a meaningful accessible name. (1.3.1, 2.4.6, 4.1.2)
  • Confirm that each tree item has a meaningful accessible name. (4.1.2)
  • Confirm that parent nodes expose the correct expanded or collapsed state and that leaf nodes do not expose aria-expanded. (4.1.2)
  • When hierarchy data cannot be calculated from DOM nesting, confirm that aria-level, aria-posinset, and aria-setsize accurately communicate the item's depth and position. (1.3.1, 4.1.2)
  • For a selectable tree, confirm that selection state is exposed accurately and consistently. (4.1.2)

  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
Screen reader
  • Confirm that the tree is announced with its accessible name and tree semantics. (4.1.2)
  • Confirm that each node is announced as a tree item with a meaningful name. (4.1.2)
  • Confirm that parent nodes announce their expanded or collapsed state. (4.1.2)
  • Confirm that hierarchy level and sibling position are available when relevant to understanding the tree. (1.3.1, 4.1.2)
  • Expand and collapse each parent node and confirm that the state updates correctly and child nodes become available or unavailable as appropriate. (4.1.2)
  • For selectable trees, confirm that selected and unselected states are announced correctly. (4.1.2)
  • For a navigation tree, confirm that destinations are understandable and that current-item information is available when applicable. (1.3.1, 2.4.4, 4.1.2)
  • For dynamic loading, confirm that loading, error, and completion messages are communicated when needed. (4.1.3)

  • WCAG 2.2: Understanding SC 2.4.4 Link Purpose (In Context) (Level A)
  • WCAG 2.2: Understanding SC 4.1.2 Name, Role, Value (Level A)
  • WCAG 2.2: Understanding SC 4.1.3 Status Messages (Level AA)
Keyboard only
  • Use Tab and Shift+Tab to move into and out of the tree. Confirm that the tree has one normal tab stop and does not create a keyboard trap. (2.1.1, 2.1.2, 2.4.3)
  • Use Down Arrow to move focus to the next visible node and Up Arrow to move focus to the previous visible node. Confirm that collapsed descendants are skipped. (2.1.1, 2.4.3)
  • On a collapsed parent node, use Right Arrow to expand it without moving focus. On an expanded parent node, use Right Arrow to move focus to its first child. (2.1.1)
  • On an expanded parent node, use Left Arrow to collapse it. On a closed parent or leaf node, use Left Arrow to move focus to its parent node. (2.1.1)
  • Use Home to move focus to the first visible node and End to move focus to the last visible node. (2.1.1)
  • Use character keys to test type-ahead navigation when the tree provides it. Confirm that focus moves predictably to a matching node. (2.1.1)
  • Use Enter or Space to perform the documented default action or selection behavior for the focused node. (2.1.1)
  • For a multi-select tree, test the documented selection command and confirm that it changes selection without moving focus or causing an unexpected context change. (2.1.1, 2.4.3, 3.2.2)
  • Confirm that the focused tree item has a visible focus indicator and is not completely hidden by other content. (2.4.7, 2.4.11)
  • Confirm that moving focus through the tree does not automatically navigate to a different page or otherwise change context. (3.2.1)

  • WCAG 2.2: Understanding SC 2.4.11 Focus Not Obscured (Minimum) (Level AA)
  • WCAG 2.2: Understanding SC 3.2.1 On Focus (Level A)
  • WCAG 2.2: Understanding SC 3.2.2 On Input (Level A)
Expanded, selected, and active states
  • Expand and collapse every type of parent node. Confirm that the visible children, programmatic state, and keyboard navigation remain synchronized. (1.3.1, 2.1.1, 4.1.2)
  • Confirm that collapsed child nodes cannot receive keyboard focus or be operated while hidden. (2.1.1, 2.4.3)
  • For a single-select tree, select different nodes and confirm that selection is removed from the prior item and communicated on the newly selected item. (4.1.2)
  • For a multi-select tree, select and deselect several nodes and confirm that each state is communicated accurately. (4.1.2)
  • Confirm that focus and selection remain distinguishable where they represent different states. (1.4.1, 4.1.2)
  • For a navigation tree, activate a node and confirm that the expected destination opens and that focus moves to a logical location in the new content when needed. (2.4.3, 2.4.4)

Inspect visual aspects
  • Check contrast for node labels, branch indicators, icons that convey node type or state, selection indicators, and focus indicators. (1.4.3, 1.4.11)
  • Confirm that expanded/collapsed, selected/unselected, focused/unfocused, and current-item states are not distinguished by color alone. (1.4.1)
  • Check the tree at 200% text resize, a 320-CSS-pixel-wide viewport, and with text-spacing overrides. Node labels, controls, indentation, instructions, and status messages must remain visible, usable, and unclipped. (1.4.4, 1.4.10, 1.4.12)
  • Confirm that hierarchical indentation and branch controls remain understandable and usable at narrow widths and high zoom. (1.4.10)
  • Confirm that each tree item and any separate expand/collapse or action control meets the minimum target size or has sufficient spacing from adjacent targets. (2.5.8)
  • Confirm that the focus indicator is visible against surrounding colors and is not completely hidden by other content. (1.4.11, 2.4.11)
  • Confirm disabled styling does not make a node's name, state, or availability impossible to understand when users need that information. (1.4.3, 1.4.11)
